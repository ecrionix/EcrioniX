Module 1 · Engineering Core

Static Timing Analysis Fundamentals

Static Timing vs. Dynamic Simulation

Static Timing Analysis (STA) is a static verification technique that exhaustively proves that all synchronous timing constraints are met across all legal signal paths, operating modes, and process corners without applying functional input vectors or testbenches. Dynamic gate-level simulation (GLS) tests only a tiny fraction of functional state-space trajectories ($< 0.01\%$), whereas STA guarantees $100\%$ path coverage across billions of potential state transitions.

Characteristic Static Timing Analysis (STA) Dynamic Simulation (GLS)
Coverage 100% exhaustive across all paths and corners. Limited strictly to exercised testbench vectors.
Execution Speed Minutes to hours for 500M+ gate SoCs. Weeks to months (computationally prohibitive).
Input Vectors None required; reads netlist + SDC + .lib + SPEF. Requires complex VCD/FSDB stimulus testbenches.
Signoff Authority Industry-standard golden signoff (PrimeTime / Tempus). Secondary functional sanity check (X-propagation).

Timing Paths: Startpoints, Endpoints, and Types

Every static timing path is bounded by a valid Startpoint and Endpoint:

  • Startpoints: Primary input ports (`in_data[*]`) or clock pins of sequential cells (Flip-Flop `CLK`, Latch `G`). Data launches on the active clock edge.
  • Endpoints: Sequential data pins (Flip-Flop `D`, Latch `D`), clock-gating enable pins (`ICG/E`), or primary output ports (`out_data[*]`). Data is captured and held stable.
Path Classification Startpoint Endpoint Governing SDC Constraints
Reg-to-Reg Launch FF Clock Pin (`CLK`) Capture FF Data Pin (`D`) create_clock, set_clock_uncertainty
In-to-Reg Top-Level Input Port Capture FF Data Pin (`D`) set_input_delay, set_driving_cell
Reg-to-Out Launch FF Clock Pin (`CLK`) Top-Level Output Port set_output_delay, set_load
In-to-Out (Feedthrough) Top-Level Input Port Top-Level Output Port set_input_delay + set_output_delay / set_max_delay

Slack, WNS, and TNS

Slack ($S$) is the difference between Data Required Time and Data Arrival Time:

  • Setup Slack: $S_{ ext{setup}} = T_{ ext{required}} - T_{ ext{arrival}}$. Positive slack indicates timing is met; negative slack indicates timing violation.
  • Hold Slack: $S_{ ext{hold}} = T_{ ext{arrival}} - T_{ ext{required}}$. Positive slack indicates data remained stable long enough.
  • Worst Negative Slack (WNS): The single worst negative slack value among all violating paths in a path group or design. Represents the absolute clock period deficit.
  • Total Negative Slack (TNS): The scalar sum of negative slack across all violating endpoints. Reflects the total magnitude of timing debt across the chip.
How Claude Accelerates STA Fundamentals Triage
Claude parses raw tool outputs, maps paths to their respective startpoint/endpoint categories, calculates WNS and TNS per clock domain, and flags whether violations are isolated anomalies (single high WNS) or systemic architectural bottlenecks (massive TNS wall with thousands of failing endpoints).
Module 2 · Timing Checks

Setup Timing Analysis: Mechanics, Decomposition & Diagnostics

The Mathematical Setup Constraint (Max Delay Check)

Setup timing ensures that data launched from register $A$ propagates through combinational logic and interconnect, arriving at register $B$ before the capture clock edge, and remaining stable for at least the library setup time ($T_{ ext{setup}}$):

Full Setup Timing Equations
$$ ext{Data Arrival} = T_{ ext{launch\_latency}} + T_{ ext{CK} o ext{Q}} + \sum T_{ ext{cell}} + \sum T_{ ext{net}}$$ $$ ext{Data Required} = T_{ ext{period}} + T_{ ext{capture\_latency}} - T_{ ext{setup}} - T_{ ext{uncertainty}} + T_{ ext{CPPR}}$$ $$ ext{Slack}_{ ext{setup}} = ext{Data Required} - ext{Data Arrival} \ge 0$$

Decomposing Negative Slack: Cell Delay vs. Net Delay

When an engineer inspects a timing report with negative slack, the first diagnostic step is calculating the Cell-to-Net Delay Ratio:

Net Delay % Cell Delay % Primary Physical Root Cause Recommended Engineering Action
> 45% < 55% Interconnect congestion, long wire detours, layer promotion failure, high coupling cap. Insert repeater buffers, promote critical net to top thick metals (M6/M7), add physical placement bounds.
< 30% > 70% Excessive logic depth, weak gate drive strength, high fanin cascade, standard-Vt or high-Vt cells. Upsize driving cells, swap critical gates to LVT/ULVT, restructure Boolean logic cones in RTL.
30% – 45% 55% – 70% Balanced path with cascading transition degradation or high fanout net driving intermediate gates. Buffer high-fanout net, clean up max-transition violations, optimize CTS clock latency.

Impact of Slew (Transition Time) and Capacitance

Standard cell delay is characterized in Liberty (.lib) files as a 2D non-linear delay lookup table indexed by Input Slew ($T_{ ext{trans}}$) and Output Load Capacitance ($C_{ ext{load}}$): $$T_{ ext{cell}} = f(T_{ ext{in\_slew}}, C_{ ext{out\_load}})$$ A single weak buffer driving a high-capacitance net causes its output slew to degrade (e.g. from 40 ps to 180 ps). This slow transition cascades into the next 4 logic stages, multiplying gate delays by up to $3 imes$. Claude scans the path for pins with transition times exceeding 80–100 ps and flags them as driver starvation bottlenecks.

Module 3 · Race Conditions

Hold Timing Analysis: Short Paths, Skew & Delay Buffering

The Mathematical Hold Constraint (Min Delay Check)

Unlike setup timing (which checks if data arrives before the next clock edge), hold timing verifies that data launched by active clock edge $N$ does not race through fast logic and overwrite data captured by the same clock edge $N$ at the receiving register:

Full Hold Timing Equations
$$ ext{Data Arrival} = T_{ ext{launch\_latency}} + T_{ ext{CK} o ext{Q}} + T_{ ext{comb\_min}} + T_{ ext{net\_min}}$$ $$ ext{Data Required} = T_{ ext{capture\_latency}} + T_{ ext{hold}} + T_{ ext{uncertainty}} - T_{ ext{CPPR}}$$ $$ ext{Slack}_{ ext{hold}} = ext{Data Arrival} - ext{Data Required} \ge 0$$

Why Fast/Cold Corners Dominate Hold Violations

Hold constraints do not depend on clock period ($T_{ ext{period}}$). Therefore, hold violations cannot be fixed by lowering clock frequency in the lab! A chip with a hold violation on silicon is permanently dead.

Hold violations peak at the Fast-Fast-Global (FFG) corner at maximum operating voltage (e.g. 0.85V) and extreme temperatures ($-40^\circ ext{C}$ or $125^\circ ext{C}$), where transistor channel conductances are highest and parasitic wire delays are lowest.

Clock Skew: The Primary Amplifier of Hold Failures

In the hold equation, positive clock skew ($\Delta T_{ ext{skew}} = T_{ ext{capture}} - T_{ ext{launch}} > 0$) directly increases Data Required Time, stealing margin from the data path. If capture latency is 400 ps and launch latency is 250 ps ($\Delta T_{ ext{skew}} = +150\, ext{ps}$), and $T_{ ext{hold}} = 30\, ext{ps}$, data must take at least 180 ps to arrive. On a shift register with 0 combinational gates ($T_{ ext{CK} o ext{Q}} pprox 70\, ext{ps}$), a severe hold violation of $-110\, ext{ps}$ is guaranteed.

Hold Buffer Insertion Strategy & Side Effects

Consideration Best Practice Rule Engineering Risk / Side Effect
Buffer Selection Use dedicated non-inverting delay cells (`DELAY_X1`, `DELAY_X2`) or clock buffers (`CLKBUF_X1`). Avoid high-drive inverters that introduce asymmetric rise/fall hold skews.
Buffer Placement Place delay buffers physically adjacent to the capture flip-flop $D$ pin. Placing near launch pin can delay branches feeding other setup-critical endpoints.
Setup Margin Safety Ensure target path has setup margin $> T_{ ext{inserted\_delay}} + 40\, ext{ps}$ at worst slow corner. Fixing hold blindly causes setup timing regressions on common functional paths.
Dynamic Power & Area Bundle multiple parallel short paths into multi-bit delay cells where supported. Inserting thousands of hold buffers consumes routing tracks and increases leakage.

Module 5 · Timing Constraints

SDC Constraint Analysis: Syntax, Pitfalls & Automated Review

Core SDC Commands and Invariant Signoff Rules

Synopsys Design Constraints (SDC) define the physical clock environment, external board interfaces, and intentional timing exceptions. A bug in SDC either causes an EDA tool to optimize phantom paths (wasting power/area) or masks real silicon violations (causing chip death).

SDC Command Primary Function Critical Verification Check
create_clock Defines master clock at primary input pin or internal oscillator pin. Explicit waveform: -period 1.0 -waveform {0.0 0.5}. Never leave waveform default unless 50% duty cycle is intended.
create_generated_clock Defines divided, multiplied, or inverted clock derived from master. Must include -source pointing to physical pin, and explicit -divide_by or -multiply_by.
set_input_delay Specifies external board trace delay from external launch clock edge. Always specify both -max (setup budget) and -min (hold budget).
set_output_delay Specifies external board setup/hold requirement outside the chip. Ensure reference clock is synchronous to the interface domain or use virtual clock.
set_clock_uncertainty Reserves timing margin for PLL jitter, duty-cycle distortion, and OCV. Pre-CTS includes clock jitter + tree skew; Post-CTS includes jitter only (skew is propagated).
set_false_path Instructs STA tool to completely ignore timing between specified pins. Strictly for asynchronous resets or static test modes. Never apply to active functional paths to eliminate violations!
set_multicycle_path Relaxes setup check by $N$ clock cycles for multi-cycle arithmetic logic. Mandatory rule: set_multicycle_path N -setup must be paired with set_multicycle_path (N-1) -hold!
set_clock_groups Declares clock domains asynchronous, exclusive, or logically independent. Verify sub-clocks derived from the same PLL are not accidentally cut with -asynchronous.

The Classic Multicycle Path Hold Trap

When an engineer writes:
set_multicycle_path 2 -setup -from [get_pins u_fsm/reg/Q] -to [get_pins u_alu/reg/D]
The tool moves the setup check to edge 2. However, by default, the hold check remains anchored to one cycle before the setup check (edge 1)! This forces the data to take at least 1 full clock cycle of delay, creating massive hold violations.

constraints/correct_multicycle_pair.sdc 
# The Invariant SDC Pair for 2-Cycle Multicycle Path
set_multicycle_path 2 -setup -from [get_pins u_fsm/state_reg*/Q] -to [get_pins u_mult/acc_reg*/D]
set_multicycle_path 1 -hold  -from [get_pins u_fsm/state_reg*/Q] -to [get_pins u_mult/acc_reg*/D]
Module 6 · Clock Networks

Clock and Timing Analysis: Skew, CPPR, Gating & Resets

Clock Network Dynamics: Latency, Skew & Common Path Pessimism

The clock distribution network delivers clock pulses to every sequential storage element in the SoC. In deep sub-micron FinFET designs, clock tree propagation delay (latency) can exceed several clock cycles.

Clock Common Path Pessimism Removal (CPPR / CRPR)

Under On-Chip Variation (OCV), STA tools apply late derate factors ($1 + \delta$) to the launch clock path and early derate factors ($1 - \delta$) to the capture clock path. However, for register pairs sharing common clock tree buffers (from the clock root down to the branch divergence point), a physical buffer cannot simultaneously be fast for capture and slow for launch at the exact same instant in time!

CPPR Mathematical Formulation
$$ ext{CPPR Credit} = T_{ ext{common\_path\_late}} - T_{ ext{common\_path\_early}}$$ This difference is added back into Data Required Time for setup checks (and subtracted for hold checks). Claude reviews timing path reports to confirm CPPR is active:
set_app_var timing_remove_clock_reconvergence_pessimism true

Clock Gating Checks (Integrated Clock Gating - ICG)

To eliminate dynamic clock switching power in idle modules, Integrated Clock Gating (ICG) cells gate the clock. A standard active-high ICG consists of a negative-edge latch feeding an AND gate:

  • ICG Setup Check: The enable signal ($E$) must arrive and set up at the latch input before the clock transitions low ($T_{ ext{clk}} = 0$). If $E$ toggles while the clock is high, a truncated clock glitch is transmitted to downstream registers.
  • ICG Hold Check: The enable signal must remain stable for the required hold time after the falling edge of the clock.

Recovery and Removal: Asynchronous Reset Timing

Check Definition Analogy Failure Result
Recovery ($T_{ ext{rec}}$) Minimum time asynchronous reset deassertion must precede the active clock edge. Setup check on reset pin. Flip-flop enters metastable state; unknown reset exit state across registers.
Removal ($T_{ ext{rem}}$) Minimum time asynchronous reset must remain asserted after the active clock edge. Hold check on reset pin. Register deasserts reset too early, capturing illegal combinational state.
Module 7 · Closure Engineering

Timing Closure: Systematic Optimization, Sizing & ECO Workflows

Systematic Timing Closure Hierarchy

Timing closure is the methodical convergence of WNS and TNS to zero across all signoff scenarios. Rather than randomly running automated ECO tools, an expert STA engineer applies precision interventions in order of increasing risk and cost:

Optimization Tactic Physical Mechanism Primary Benefit Design Side Effect & Risk
Vt Swapping (LVT/ULVT) Modifies transistor threshold implant without changing cell footprint or placement. 15%–30% cell delay reduction with zero physical routing disturbance. Sub-threshold leakage power increases exponentially ($10 imes$ higher for ULVT).
Driver Upsizing (e.g. X1 → X4) Increases transistor channel width to lower driving resistance. Sharpens output transition and reduces cell internal delay under load. Increases input pin capacitance seen by the preceding logic stage.
Buffer Insertion Breaks long distributed RC interconnects into shorter, linear delay segments. Reduces total net delay ($T_{ ext{net}} \propto L^2 o rac{L^2}{N}$). Requires legal placement site; risks local cell congestion.
Pin Swapping Swaps logically equivalent input pins on multi-input gates (e.g., NAND3 A vs C). Assigns critical signal to internal pin with fastest internal path to output. Zero power or area cost; verified automatically by Formality/LEC.
Useful Skew Scheduling Intentionally delays capture clock on setup-critical endpoints using CTS latency. Borrow cycle time from subsequent non-critical downstream pipeline stages. Eats into hold margin on the same register; must be bounded strictly.

Module 8 · Advanced Signoff

Advanced STA: OCV, AOCV, POCV/LVF, Crosstalk & Temperature Inversion

Evolution of Variation Modeling: From Flat OCV to POCV / LVF

As process geometries scaled below 16nm FinFET into 5nm/3nm Gate-All-Around (GAA), random microscopic variations — such as Random Dopant Fluctuation (RDF), line-edge roughness (LER), and work-function variation — made classical flat margin derating obsolete.

Variation Paradigm Mathematical Principle Pessimism Level Applicable Nodes
Flat OCV Applies uniform global derate (e.g. Late $+8\%$, Early $-8\%$) to every cell. Extreme pessimism on deep paths; causes over-design. Legacy planar nodes (> 40nm).
AOCV (Stage-Based) Derate factor scales down as path logic depth increases ($ ext{Derate} \propto rac{1}{\sqrt{N}}$). Moderate; accounts for statistical cancellation of independent cell variations. Mature FinFET nodes (28nm – 16nm).
POCV / LVF Models delay as nominal plus statistical sigma ($T_{ ext{cell}} = \mu \pm 3\sigma$). Physically realistic; captures asymmetric Gaussian and non-Gaussian tails. Advanced FinFET / GAA (7nm, 5nm, 3nm, Intel 18A).

Signal Integrity (SI) & Crosstalk Delay (Miller Effect)

When two adjacent parallel metal wires run alongside each other, capacitive coupling ($C_c$) accounts for up to 75% of total wire capacitance. The dynamic switching relationship between the Aggressor net and Victim net alters delay dramatically:

  • Opposite-Direction Switching (Setup Penalty): If victim net falls ($1 o 0$) while aggressor rises ($0 o 1$), voltage delta across $C_c$ is $2V_{DD}$. By the Miller effect, effective capacitance doubles ($C_{ ext{eff}} pprox C_{ ext{ground}} + 2C_c$), significantly slowing signal transition and worsening setup slack.
  • Same-Direction Switching (Hold Penalty): If both nets switch simultaneously in the same direction, voltage delta across $C_c$ is $0V$. Effective capacitance drops ($C_{ ext{eff}} pprox C_{ ext{ground}}$), accelerating transition and creating unexpected hold violations.

Temperature Inversion Phenomenon

In legacy planar CMOS, cells are always slowest at high temperatures ($125^\circ ext{C}$) due to reduced carrier mobility ($\mu \propto T^{-1.5}$). However, in FinFET nodes operating at ultra-low supply voltages ($V_{DD} \le 0.75\, ext{V}$), threshold voltage reduction ($V_{ ext{th}}$ decreases as temperature drops) dominates over carrier mobility.

Temperature Inversion Signoff Reality
At low $V_{DD}$, transistors exhibit worse propagation delay at $-40^\circ ext{C}$ than at $125^\circ ext{C}$! A design that meets setup timing at $125^\circ ext{C}$ will fail catastrophically at $-40^\circ ext{C}$. Claude explicitly prompts engineers to inspect cold corners for setup closure in advanced FinFET signoff.

Timing Report Automation: Python Parsers & PrimeTime Tcl Pipelines

Automating Multi-Corner STA Triage

Modern ASIC projects execute timing analysis across 30+ MMMC scenarios, generating hundreds of gigabytes of text reports. Claude assists STA engineers in developing automated Python and Tcl pipelines to parse, summarize, and correlate violations across runs.

scripts/automation/parse_sta_report.py (Complete Standalone Parser) 
import re
import csv
import sys

def parse_sta_timing_report(report_path, output_csv="timing_summary.csv"):
    with open(report_path, 'r', encoding='utf-8') as f:
        content = f.read()

    # Split report into individual timing paths
    paths = content.split("Startpoint:")
    parsed_records = []

    for path_str in paths[1:]:
        full_path = "Startpoint:" + path_str
        startpoint = re.search(r"Startpoint:\s+([^\s\(\)]+)", full_path)
        endpoint   = re.search(r"Endpoint:\s+([^\s\(\)]+)", full_path)
        path_group = re.search(r"Path Group:\s+([^\s]+)", full_path)
        path_type  = re.search(r"Path Type:\s+([^\s]+)", full_path)
        slack_m    = re.search(r"slack\s+\((VIOLATED|MET)\)\s+([-\d\.]+)", full_path)

        # Calculate cell vs net delay components
        net_delays = [float(x) for x in re.findall(r"\(net[^\)]*\)\s+([\d\.]+)", full_path)]
        total_net  = sum(net_delays)
        arrival_m  = re.search(r"data arrival time\s+([\d\.]+)", full_path)

        if startpoint and endpoint and slack_m:
            s_name  = startpoint.group(1)
            e_name  = endpoint.group(1)
            p_group = path_group.group(1) if path_group else "UNKNOWN"
            p_type  = path_type.group(1) if path_type else "max"
            status  = slack_m.group(1)
            slack   = float(slack_m.group(2))
            t_arr   = float(arrival_m.group(1)) if arrival_m else 1.0

            net_pct = (total_net / t_arr) * 100 if t_arr > 0 else 0.0

            parsed_records.append({
                "Startpoint": s_name,
                "Endpoint": e_name,
                "PathGroup": p_group,
                "Type": p_type,
                "Status": status,
                "Slack_ns": slack,
                "NetDelay_ns": round(total_net, 4),
                "NetDelay_Pct": round(net_pct, 1),
                "Diagnosis": "Net Detour / Congestion" if net_pct > 45 else "Logic Depth / Sizing"
            })

    # Export to CSV
    if parsed_records:
        keys = parsed_records[0].keys()
        with open(output_csv, 'w', newline='', encoding='utf-8') as f:
            dict_writer = csv.DictWriter(f, fieldnames=keys)
            dict_writer.writeheader()
            dict_writer.writerows(parsed_records)
        print(f"Successfully parsed {len(parsed_records)} paths to {output_csv}")
    else:
        print("No valid timing paths found in report.")

if __name__ == "__main__":
    if len(sys.argv) > 1:
        parse_sta_timing_report(sys.argv[1])
    else:
        print("Usage: python parse_sta_report.py ")

Timing Debugging Scenarios with Claude: Real-World Investigations

Scenario 1: Negative Setup Slack on High-Fanout ALU Control Net

Evidence Presented: PrimeTime report shows -215 ps slack on 32-bit ALU carry path. Logic depth is 14 levels. Net n_alu_op_sel has a fanout of 48 with net delay of 280 ps and transition time of 165 ps.

Claude Diagnostic Reasoning: The logic depth itself is within target bounds, but the driver of n_alu_op_sel is a minimum-drive cell (INV_X1) struggling to charge the gate capacitances of 48 standard cells. Slew degradation accounts for over 180 ps of excess gate delay.

Prescribed Solution: Build a balanced buffer tree using insert_buffer with a fanout limit of 8 (e.g. BUF_X8 feeding 6 BUF_X4 cells) or upsize driver to INV_X16. Slack recovers by +190 ps.

Scenario 2: Negative Hold Slack on Scan Register Chain Post-CTS

Evidence Presented: Post-CTS min-delay report reveals -95 ps hold slack between r_scan_ff_0 and r_scan_ff_1. Path has 0 combinational gates ($T_{ ext{CK} o ext{Q}} = 85\, ext{ps}$). Clock skew between registers is $+140\, ext{ps}$.

Claude Diagnostic Reasoning: The registers are logically adjacent in the scan chain but physically placed 250 μm apart across different clock tree branch buffers, creating 140 ps of positive clock skew that overwhelms the 85 ps propagation delay.

Prescribed Solution: Reorder the scan chain based on physical flip-flop locations (Innovus scanReorder or ICC2 reorder_scan_chains) or insert two DELAY_X2 hold buffers near the capture register $D$ pin.

Scenario 3: Unexpected Clock Skew across Core Partitions

Evidence Presented: CCOpt skew report shows 380 ps global skew between CPU core and Crypto co-processor (target: < 100 ps).

# STA Report Analyzer Skill

## Purpose
Performs deep structural dissection of Synopsys PrimeTime or Cadence Tempus timing reports (`report_timing -significant_digits 4 -net -capacitance -transition_time -input_pins`), separating launch clock latency, CK-to-Q delay, combinational logic delay, interconnect RC delay, capture clock latency, and clock uncertainty.

## When to Activate
Activate when evaluating any `.tarpt` or `.rpt` timing path with negative slack, or when conducting post-synthesis, post-CTS, or post-route timing reviews.

## Required Input Files
- Detailed path report (`report_timing -delay_type max/min -max_paths 1 -input_pins -nets -capacitance -transition_time`)
- Standard cell library PVT corner context (e.g., SSG 0.65V -40C or FFG 0.85V 125C)
- SDC clock frequency and clock uncertainty definitions

## Step-by-Step Analysis Workflow
1. **Header & Context Verification:**
   - Extract Startpoint, Endpoint, Path Group, Path Type (max/min), and Corner.
   - Verify whether the path is register-to-register, input-to-register, register-to-output, or feedthrough.
2. **Clock Tree Breakdown:**
   - Calculate Launch Clock Latency ($T_{\text{launch}}$) and Capture Clock Latency ($T_{\text{capture}}$).
   - Compute Clock Skew ($\Delta T_{\text{skew}} = T_{\text{capture}} - T_{\text{launch}}$ for setup; opposite for hold).
   - Check Clock Uncertainty ($T_{\text{uncert}}$) and CPPR/CRPR credit.
3. **Data Path Delay Decomposition:**
   - Separate Launch Flip-Flop $T_{\text{CK}\to\text{Q}}$.
   - Sum combinational cell delays ($\sum T_{\text{cell}}$).
   - Sum interconnect net delays ($\sum T_{\text{net}}$).
   - Calculate **Cell-to-Net Delay Ratio**: $\frac{\sum T_{\text{net}}}{T_{\text{datapath}}} \times 100\%$.
4. **Bottleneck Cell & Net Pinpointing:**
   - Identify nets with excessive transition time ($T_{\text{trans}} > 100\,\text{ps}$) or high capacitive loading ($C_{\text{load}} > 30\,\text{fF}$).
   - Flag high-fanout nets ($\text{Fanout} > 16$) or physical placement detours.
   - Flag weak drive strength cells (e.g., `_X1` or `_X0.5`) in the critical logic cone.

## Example Input
```text
  Startpoint: u_core/u_alu/r_operand_a_reg_15/CLK (DFCNQD1)
  Endpoint:   u_core/u_alu/r_result_reg_31/D (DFCNQD1)
  Path Group: CLK_CORE
  Path Type:  max
  Data Arrival Time: 1.482 ns
  Data Required Time: 1.250 ns
  Slack: -0.232 ns (VIOLATED)
  Net Delay on n_alu_carry: 0.310 ns (fanout=24)
```

## Expected Output
- **Path Summary Matrix:** Startpoint, Endpoint, Slack, Corner, Clock Skew, Logic Depth.
- **Delay Ratio Analysis:** Cell Delay % vs Net Delay %.
- **Bottleneck Hierarchy:** Top 3 gates/nets causing > 60% of data path delay.
- **Prescribed ECO Tactics:** Buffer insertion, cell upsizing, or Vt swapping.

## Limitations
- Claude cannot calculate SPICE non-linear delay tables or 3D field extraction parasitics. All recommended delay reductions are engineering estimates; PrimeTime/Tempus signoff is mandatory.

## Verification Checklist
- [ ] Clock period and uncertainty validated against golden SDC.
- [ ] Transition times checked against library max_transition limits.
- [ ] ECO sizing does not induce new hold violations or max-capacitance violations.

# Setup Timing Debugger Skill

## Purpose
Systematically analyzes negative setup slack ($S_{\text{setup}} = T_{\text{required}} - T_{\text{arrival}} < 0$), determining whether the failure stems from architectural logic depth, weak cell drive strength, interconnect RC delay, clock network latency mismatch, or over-constrained SDC budgets.

## When to Activate
Activate when analyzing setup WNS/TNS regressions after synthesis, placement optimization, CTS, or detailed routing.

## Mathematical Formulation
$$\text{Data Arrival} = T_{\text{launch\_latency}} + T_{\text{CK}\to\text{Q}} + \sum T_{\text{cell}} + \sum T_{\text{net}}$$
$$\text{Data Required} = T_{\text{period}} + T_{\text{capture\_latency}} - T_{\text{setup}} - T_{\text{uncertainty}} + T_{\text{CPPR}}$$
$$\text{Slack}_{\text{setup}} = \text{Data Required} - \text{Data Arrival}$$

## Diagnostic Decision Tree
1. **Is Net Delay > 45% of Data Path Delay?**
   - *Yes:* Placement detour, high routing congestion, or unbuffered long net. Solution: Buffer insertion, layer promotion, or physical cell padding.
2. **Is Logic Depth > 20 levels for 1 GHz+ targets?**
   - *Yes:* Combinational logic cascade too deep. Solution: Architectural pipelining, register retiming, or logic restructuring.
3. **Are Input Transition Times > 120 ps on Critical Pins?**
   - *Yes:* Output driver starvation. Solution: Gate upsizing (e.g. `_X1` $\to$ `_X4`) or buffer insertion.
4. **Is Capture Clock Significantly Earlier than Launch Clock ($\Delta T_{\text{skew}} < -80\,\text{ps}$)?**
   - *Yes:* Clock tree imbalance. Solution: Useful skew scheduling or CTS trunk rebalancing.

## Limitations
- Setup fixes (upsizing, LVT swapping) increase dynamic and leakage power, and can create hold violations at fast/cold corners.

## Verification Checklist
- [ ] Setup slack verified under Slow-Slow-Global (SSG) corner at minimum $V_{DD}$.
- [ ] Proposed cell resizing evaluated against cell footprint compatibility.
- [ ] Downstream hold margin verified at Fast-Fast-Global (FFG) corner.

# Hold Timing Debugger Skill

## Purpose
Investigates hold timing violations ($S_{\text{hold}} = T_{\text{arrival}} - T_{\text{required}} < 0$), ensuring data remains stable past the active capture clock edge to prevent race conditions and functional latch-up.

## Mathematical Formulation
$$\text{Data Arrival} = T_{\text{launch\_latency}} + T_{\text{CK}\to\text{Q}} + T_{\text{comb\_min}} + T_{\text{net\_min}}$$
$$\text{Data Required} = T_{\text{capture\_latency}} + T_{\text{hold}} + T_{\text{uncertainty}} - T_{\text{CPPR}}$$
$$\text{Slack}_{\text{hold}} = \text{Data Arrival} - \text{Data Required}$$

## Step-by-Step Analysis Workflow
1. **Corner Verification:** Confirm report is from Fast-Fast-Global (FFG) or Fast-Cold (0.85V, -40C / 125C) corner where silicon propagation is fastest.
2. **Data Path Inspection:** Measure logic depth. Many hold failures occur on shift registers, scan chains, or pipeline stages with 0 combinational gates between launch Q and capture D.
3. **Clock Skew Evaluation:** Check if capture clock latency exceeds launch clock latency ($\Delta T_{\text{skew}} = T_{\text{capture}} - T_{\text{launch}} > 0$). Excessive positive skew eats into the hold budget.
4. **Buffer Insertion Strategy:**
   - Select non-inverting delay buffers (`CLKBUF_X1`, `DELAY_X2`).
   - Place delay buffers physically close to the capture register D pin to minimize routing disruption.
   - Verify that adding delay does not turn a positive setup slack path negative at the slow corner.

## Limitations
- Adding excessive hold buffers increases standard cell density and dynamic switching power. Hold fixes must never be committed without multi-corner setup verification.

## Verification Checklist
- [ ] Hold analysis executed with on-chip variation derates and CPPR enabled.
- [ ] Setup slack margin confirmed $\ge T_{\text{inserted\_delay}} + 30\,\text{ps}$ at worst setup corner.
- [ ] Delay buffer footprint exists in standard cell target library.

# Clock Skew Analyzer Skill

## Purpose
Evaluates post-CTS and post-route clock latency reports, distinguishing between harmless global skew across non-communicating blocks and dangerous local skew between synchronous launch-capture register pairs.

## Analysis Workflow
1. **Global Skew Evaluation:**
   - $\text{Global Skew} = \max(T_{\text{latency}}) - \min(T_{\text{latency}})$ across the entire clock tree.

3. **Useful Skew Verification:**

## Limitations
- Clock latency values depend on extracted clock tree parasitic accuracy; pre-CTS estimations are purely speculative.

## Verification Checklist
- [ ] Local skew between critical communicating registers $< 40\,\text{ps}$.
- [ ] Clock buffers balanced symmetrically in technology library.

# OCV, AOCV & POCV Reviewer Skill

## Purpose
Audits statistical timing derates and on-chip variation configurations in PrimeTime and Tempus, verifying that margin models match foundry signoff guidelines without introducing excessive pessimism.

## Methodology Comparison
- **Traditional OCV:** Applies flat percentage derates (e.g., $+5\%$ late, $-5\%$ early) across the entire chip. Highly pessimistic on deep paths.

## Key Audit Checks
1. Verify `set_timing_derate` statements match foundry signoff runsets.
2. Confirm Clock Common Path Pessimism Removal (CPPR / CRPR) is enabled:
   `set_app_var timing_remove_clock_reconvergence_pessimism true`
3. Check POCV sigma threshold setting (typically $3\sigma$).

## Limitations
- Liberty Variation Format (LVF) tables are proprietary foundry IP; Claude analyzes derate commands and reports, not raw cell characterization tables.

## Verification Checklist
- [ ] CPPR enabled and validated in timing reports.
- [ ] POCV derate tables loaded and applied to both data and clock paths.

# SI Crosstalk Timing Reviewer Skill

## Purpose
Inspects PrimeTime SI or Tempus SI crosstalk analysis outputs, evaluating how dynamic switching on aggressor nets impacts victim net propagation delay (Miller effect) and functional voltage glitch noise.

## Physics Evaluated
- **Crosstalk Setup Delay:** Aggressor switching in opposite direction increases effective coupling capacitance ($C_{\text{eff}} \approx 2 \cdot C_c$), expanding transition time and causing setup violations.

## Prescribed Physical Fixes
1. Upsize victim driver to lower driving impedance.
2. Downsize aggressor driver if aggressor path has excess slack.
3. Insert repeater buffer on long victim interconnect.
4. Shield victim net with VDD/VSS tracks or increase routing track spacing.

## Limitations
- SI calculation requires accurate coupled parasitic extraction (`*C_COUP` in SPEF); lumped capacitance is completely inadequate for SI signoff.

## Verification Checklist
- [ ] Extracted SPEF contains explicit cross-coupling capacitors.
- [ ] Peak glitch height $< 25\%$ of supply voltage ($V_{DD}$).

Project 4 Build a Python Timing Report Parser that Generates a CSV

Design Scenario: Automate the extraction of critical paths across 24 PVT corners, calculate cell-to-net delay ratios, and export a structured CSV spreadsheet for executive team reviews.

scripts/automation/sta_batch_parser.py
import re
import csv
import glob
import os

def parse_all_reports(report_dir, output_csv="summary_qor.csv"):
    files = glob.glob(os.path.join(report_dir, "*.tarpt"))
    all_data = []

    for fpath in files:
        corner_name = os.path.basename(fpath).replace(".tarpt", "")
        with open(fpath, "r", encoding="utf-8") as f:
            text = f.read()

        paths = text.split("Startpoint:")
        for p in paths[1:]:
            p_text = "Startpoint:" + p
            slack_m = re.search(r"slack\s+\((VIOLATED|MET)\)\s+([-\d\.]+)", p_text)
            if slack_m and slack_m.group(1) == "VIOLATED":
                start_m = re.search(r"Startpoint:\s+([^\s\(\)]+)", p_text)
                end_m   = re.search(r"Endpoint:\s+([^\s\(\)]+)", p_text)
                nets    = [float(x) for x in re.findall(r"\(net[^\)]*\)\s+([\d\.]+)", p_text)]
                arr_m   = re.search(r"data arrival time\s+([\d\.]+)", p_text)

                total_net = sum(nets)
                arr_time  = float(arr_m.group(1)) if arr_m else 1.0
                net_ratio = (total_net / arr_time) * 100 if arr_time > 0 else 0

                all_data.append({
                    "Corner": corner_name,
                    "Startpoint": start_m.group(1) if start_m else "N/A",
                    "Endpoint": end_m.group(1) if end_m else "N/A",
                    "Slack_ns": float(slack_m.group(2)),
                    "NetDelay_ns": round(total_net, 4),
                    "NetDelay_Pct": round(net_ratio, 1),
                    "RootCause": "Routing Detour / Fanout" if net_ratio > 45 else "Logic Cone Depth"
                })

    all_data.sort(key=lambda x: x["Slack_ns"])
    with open(output_csv, "w", newline="", encoding="utf-8") as f:
        writer = csv.DictWriter(f, fieldnames=all_data[0].keys())
        writer.writeheader()
        writer.writerows(all_data)
    print(f"Generated {output_csv} with {len(all_data)} violating paths.")

if __name__ == "__main__":
    parse_all_reports("reports/timing/")

Static Timing Analysis & AI Engineering FAQ

1. Can Claude directly execute Static Timing Analysis or calculate delay equations?

No. Claude is an LLM with no integrated numerical delay calculation engine, no non-linear delay model (NLDM) or composite current source (CCS) interpolator, and no 3D parasitic extraction solver. Claude functions as an intelligent diagnostic copilot that parses timing reports, calculates delay component ratios, detects SDC anomalies, and formulates precise Tcl ECO scripts for golden signoff execution in Synopsys PrimeTime or Cadence Tempus.

2. How does Claude differentiate between cell delay and net delay bottlenecks in an STA report?

Claude calculates the Cell-to-Net Delay Ratio across the data path. If net delay exceeds 40% to 50% of the total path arrival time, Claude identifies physical interconnect detours, high wire resistance, or high capacitive loading, recommending buffer insertion or layer promotion. If cell delay dominates (> 65%), it points to excessive logic depth, weak drive strength, or sub-optimal threshold voltage (Vt) cell variants.

3. Can Claude diagnose hold timing violations across multi-corner scenarios?

Yes. Claude evaluates min-delay timing reports at fast/cold corners (such as FFG 0.85V 125C or -40C) where silicon speed is highest. It assesses clock skew between launch and capture registers, measures minimum data path delay, and recommends non-inverting delay buffer insertions (e.g. DELAY_X2) placed close to capture registers, ensuring that proposed fixes do not degrade setup slack at slow corners.

4. How does Claude help audit SDC constraints for subtle bugs?

Claude reviews SDC files for common failure modes: unconstrained ports, generated clocks missing master source definitions, illegal set_false_path statements applied to synchronous multi-bit buses, and set_multicycle_path setup constraints that omit the required corresponding (N-1) hold multiplier.

5. What is Clock Common Path Pessimism Removal (CPPR / CRPR) and how does Claude verify it?

In static timing analysis under on-chip variation (OCV), different early and late derate factors are applied to launch and capture clock paths. However, the shared root clock tree segments cannot physically operate at two different speeds simultaneously. CPPR removes this artificial pessimism. Claude verifies that CPPR is enabled in tool settings and audits the CPPR credit line in timing path reports.

6. Is it safe to share proprietary ASIC timing reports and SDC files with Claude?

Proprietary timing paths, hierarchical instance names, and standard cell library parameters constitute trade secrets. Backend teams must never paste un-sanitized reports into public AI tools. Teams should use enterprise Claude instances under Zero Data Retention (ZDR) agreements or employ automated Python sanitization scripts to anonymize cell names, clock names, and absolute Linux file paths.

7. What are the 15 Claude Code STA skills included in this masterclass?

The 15 skills are version-controlled SKILL.md packages covering: sta-report-analyzer, setup-timing-debugger, hold-timing-debugger, sdc-constraint-reviewer, critical-path-analyzer, clock-skew-analyzer, clock-tree-timing-reviewer, mmmc-timing-analyzer, ocv-aocv-pocv-reviewer, timing-violation-classifier, timing-eco-reviewer, timing-report-comparator, sta-tcl-automation, timing-regression-analyzer, and si-crosstalk-timing-reviewer.

8. How does Claude assist with Signal Integrity (SI) and crosstalk delay analysis?

Claude parses PrimeTime SI and Tempus SI reports, identifying victim nets subjected to capacitive coupling from simultaneously switching aggressor nets (Miller effect). It calculates crosstalk-induced delay expansion and evaluates glitch height against noise margins, prescribing victim upsizing, net shielding, or repeater insertion.
