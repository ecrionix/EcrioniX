The ASIC Physical Implementation Mental Model for AI

Physics Engine Reality: Why LLMs Cannot Route or Close Timing Directly

Large Language Models like Claude operate entirely within the domain of token prediction and semantic pattern matching. Physical design in advanced FinFET and Gate-All-Around (GAA) nodes (e.g., TSMC N5/N3, Intel 18A) is fundamentally governed by computational physics, non-linear partial differential equations, and 3D electromagnetic Maxwell field solutions.

An LLM has no spatial awareness, no grid awareness, and no solver for:

  • Poisson's and Laplace's Equations: Governing electrostatic charge distribution and substrate noise coupling.
  • 3D Field Solvers: Calculating fringing, sidewall, and cross-coupling capacitances ($C_{ ext{coupling}}$) between dense sub-20nm metal wires.
  • Non-Linear Delay Models (NLDM) & Composite Current Source (CCS/ECSM): Driver waveform slicing under voltage droop and input slew variation.
  • Maze Routing & Track Assignment: Solving NP-hard graph routing on 15+ metal layers with millions of design rules.
  • Finite Element Thermal & Electromigration Modeling: Calculating Joule heating and current density limits ($J_{\max} = rac{I_{ ext{rms}}}{W imes T}$).
The Golden Rule of AI in ASIC Backend Engineering
Claude is an implementation copilot, diagnostic assistant, and script architect. It can analyze reports, interpret log files, identify bottlenecks, hypothesize root causes, and write clean Tcl scripts. However, every single AI-generated physical change must be deterministically executed and validated by commercial signoff EDA engines (Innovus, ICC2, PrimeTime, Tempus, Calibre, Voltus). Claude never "closes" timing or fixes DRCs autonomously.

The 3-Tier Physical Design Verification Contract

To deploy Claude safely in enterprise tapeout environments without risking multi-million dollar silicon respins or catastrophic schedule slips, every physical design team must enforce the 3-Tier Verification Contract:

Tier Entity Primary Responsibility Enforcement Mechanism
Tier 1: AI Advisory Claude & Claude Code Log and report triage, WNS/TNS path diagnosis, congestion pattern recognition, Tcl script generation, constraint checking, ECO hypothesis creation. Markdown audit trails, structured Tcl proposals, commit diff reviews.
Tier 2: EDA Engine Innovus, ICC2, PrimeTime, Calibre, Voltus Rigorous deterministic calculation: extraction (StarRC/Quantus), timing calculation (PrimeTime/Tempus), physical verification (Calibre nmDRC/LVS), IR drop (RedHawk/Voltus). Automated CI/CD regressions, signoff rule decks, formal equivalence checking (Formality/Conformal LEC).
Tier 3: Signoff Architect Principal PD / STA Engineer Final signoff authority: wafer margin review, signoff corner waiver signoff, foundry DFM waivers, tapeout freeze approval. Manual signoff review checklist, tapeout documentation, formal design review board signoff.

Common AI Failure Modes in Physical Design

Backend engineers working with Claude must actively guard against these specific failure modes:

  • Hallucinated Tool Commands & Obsolete Flags: LLMs frequently blend syntax across EDA tools (e.g., mixing Cadence Innovus setPlaceMode with Synopsys ICC2 set_app_options -name place.*) or invent flags (e.g., optDesign -fix_all_hold).
  • Illegal Coordinate Placement: Recommending cell sizing or buffer insertions at coordinates that overlap with hard macros, power straps, or keepout halos.
  • Fixing Setup at the Expense of Hold: Recommending aggressive driver upsizing or threshold voltage (Vt) swapping to Ultra-Low-Vt (ULVT) that cures negative setup slack (+120 ps) but creates catastrophic hold violations (-350 ps) at fast/cold corners.
  • Non-Existent Metal Layer Routing: Suggesting routing jumpers or shielding on layers outside the defined technology LEF stack (e.g., specifying Metal 11 in a 7-metal-layer cost-optimized IoT process).
  • Missing Design Rule Constraints (DRVs): Inserting wide buffers without checking whether max-capacitance or max-transition limits are exceeded on the driving pin.

Skill 01 Floorplanning: Architecture, Macro Placement & Flyline Analysis

Floorplanning establishes the physical framework for the entire SoC. A compromised floorplan guarantees downstream routing congestion, unresolvable timing violations, and severe IR drop. Claude accelerates floorplan exploration by reviewing DEF geometry scripts, auditing channel clearances, and evaluating macro orientation relative to core logic flylines.

Floorplan Key Metrics Evaluated by Claude
  • Core Utilization: Ensuring standard cell density is budgeted between 65%–75% for advanced FinFET nodes (allowing headroom for CTS buffers, hold buffers, and timing ECOs).
  • Aspect Ratio: Ratio of height to width ($H/W pprox 1.0$ for square dies; non-square ratios evaluated against package cavity and I/O bump boundaries).
  • Macro Channel Spacing: Verifying spacing between adjacent SRAM blocks satisfies:
    Channel Width ≥ 2 × (Power Stripe Width) + (Routing Pitch × Routing Layers) + Halo Clearance.
  • Pin Orientation & Halos: Ensuring macro pins face outward into standard cell channels, and hard halos (e.g. 5–10 μm) prevent standard cells from blocking macro pin access.
scripts/floorplan/refine_floorplan.tcl (Cadence Innovus / Synopsys ICC2) 
# Cadence Innovus Floorplan Refinement Script
# Initialize die boundaries: 1800um x 1800um, 70% utilization
setDieArea 0 0 1800 1800
setCoreArea 50 50 1750 1750

# Place SRAM macro banks toward periphery to leave central core contiguous
# Apply 8um hard halo around all SRAM macros to reserve routing track access
createPlaceBlockage -type hard -box {120 120 450 680} -name halo_sram_bank0
createPlaceBlockage -type routing -layers {M1 M2 M3} -box {120 120 450 680}

# Synopsys ICC2 Equivalent Commands
# initialize_floorplan -core_utilization 0.70 -shape R -side_ratio {1 1} -core_offset {50 50 50 50}
# create_keepout_margin -type hard -outer {8 8 8 8} [get_cells -filter "is_hard_macro==true"]
# set_block_pin_constraints -allowed_layers {M4 M5} -sides {1 2}

What Claude Can Do: Parse floorplan DEF/Tcl scripts; compute channel clearances; calculate standard cell core utilization; flag macro pins facing boundary walls; generate clean halo blockage scripts.

What Claude Cannot Do: Execute global routing to prove routability; guarantee zero cell overlap; replace visual GUI floorplan inspection in Innovus/ICC2.

Skill 02 Power Planning: Rings, Stripes, Rails, Mesh & IR Drop

Power planning delivers clean, robust VDD and VSS rails across the chip to ensure IR drop does not degrade transistor switching speed or cause functional hold failures. The power grid consists of:

  1. Power Rings: Outer concentric rings on top thick metals (M8/M9) encircling the core or voltage domains.
  2. Power Stripes / Mesh: Dense orthogonal grid of vertical and horizontal stripes on upper metal layers (e.g., M7 vertical, M8 horizontal) to distribute current uniformly.
  3. Standard Cell Rails: Continuous follow-pin rails on Metal 1 (or Metal 2 in modern FinFETs) powering standard cell rows.
  4. Via Stacks: Multi-cut via arrays connecting top mesh stripes through intermediate layers down to M1 rails.
scripts/power/create_power_mesh.tcl (Innovus / ICC2) 
# Cadence Innovus: Global Power Grid Synthesis
# 1. Connect Global Nets
globalNetConnect VDD -type pgpin -pin VDD -all
globalNetConnect VSS -type pgpin -pin VSS -all

# 2. Add Power Stripes on Upper Metals (M7 Vertical, M8 Horizontal)
addStripe -nets {VSS VDD} -layer M7 -direction vertical -width 3.2 -spacing 1.8           -pitch 28.0 -set_to_set_distance 28.0 -start_offset 10.0
addStripe -nets {VSS VDD} -layer M8 -direction horizontal -width 4.0 -spacing 2.0           -pitch 32.0 -set_to_set_distance 32.0 -start_offset 12.0

# 3. Standard Cell Rail Connection (sroute)
sroute -connect {blockPin padPin padRing corePin} -layerChangeRange {M1 M8}        -nets {VDD VSS} -corePinWidth 0.16 -allowJogging 1

Static vs Dynamic IR Drop: Static IR drop is caused by average DC current ($V_{ ext{drop}} = I_{ ext{avg}} imes R_{ ext{mesh}}$). Dynamic IR drop is caused by simultaneous switching noise ($L \cdot rac{di}{dt} + I_{ ext{peak}} imes R$), occurring during major clock edges. Claude parses Voltus/RedHawk summary reports to pinpoint under-designed mesh regions, inadequate via counts, or excessive decap deficiency.

Skill 03 Placement Optimization: Density, Spreading, HFNS & Timing-Driven Engine

Placement proceeds through coarse global placement (solving quadratic wirelength formulations), detailed placement (snapping standard cells into legal row sites without overlap), and placement optimization (timing-driven buffer insertion, cell resizing, and high-fanout net synthesis).

Diagnosing Congestion Hotspots During Placement
If global placement reports localized cell density exceeding 85%–90%, routing channels will be starved of horizontal and vertical routing tracks. Claude diagnoses placement log files and recommends:
  • Partial Placement Blockages: Restricting cell density to 60% in congested channels (createPlaceBlockage -type soft -density 60).
  • Cell Padding: Adding artificial halo margins around high-pin-count cells (e.g. multi-bit flip-flops, XOR arithmetic trees) to prevent dense pin clustering.
  • Scan Chain Reordering: Un-stitching and re-stitching scan flip-flops based on physical proximity rather than logical netlist order, reducing wirelength by 15%–25%.

Skill 04 Clock Tree Synthesis (CTS): Skew, Insertion Delay, Uncertainty & ICGs

The clock tree is the single most critical structural network in any synchronous digital design. CTS synthesizes an inverter/buffer tree to distribute the clock signal from the clock root (PLL/OSC) to tens or hundreds of thousands of sequential sink pins with minimal skew, minimal insertion delay (latency), and balanced duty cycle.

CTS Metric Definition Design Target Claude Diagnostic Focus
Insertion Delay Propagation delay from clock source pin to the furthest sink pin. Minimal & uniform across corners (e.g., < 800 ps at SS). Flags excessively deep buffer stages (levels > 8) or weak root drivers.
Global Skew Difference between max and min insertion delay across all sinks on the chip. < 150–250 ps across entire clock domain. Audits clock tree balance across asymmetric floorplan quadrants.
Local Skew Skew between communicating launch and capture flip-flops. < 30–50 ps for high-speed synchronous interfaces. Evaluates hold timing budget; local skew dominates hold closure.
Clock Uncertainty Margin reserved for clock jitter, PLL phase error, and OCV/AOCV/POCV variation. Pre-CTS: 150–200 ps; Post-CTS: 40–60 ps (jitter only). Ensures user does not double-count insertion delay margin after CTS.
ICG Placement Integrated Clock Gating cell positioning relative to governed sinks. ICG must sit physically close to sink cluster (< 50 μm). Checks enable setup timing to ICG E pin; avoids long enable detours.
scripts/cts/ccopt_spec.tcl (Cadence Innovus CCOpt) 
# Cadence Innovus CCOpt (Clock Concurrent Optimization) Configuration
create_ccopt_clock_tree_spec
set_ccopt_property target_skew 0.080 ;# 80 ps target skew
set_ccopt_property target_max_trans 0.120 ;# 120 ps max transition
set_ccopt_property buffer_cells {CLKBUF_X4 CLKBUF_X8 CLKBUF_X12 CLKBUF_X16}
set_ccopt_property inverter_cells {CLKINV_X4 CLKINV_X8 CLKINV_X12 CLKINV_X16}
set_ccopt_property route_type_top default_clock_route_top ;# 2W2S on M5/M6 with VSS shielding
set_ccopt_property route_type_trunk default_clock_route_trunk
ccopt_design -cts

Skill 05 Routing: Global Routing, Track Assignment, Detailed Routing & DRC

Routing translates logical netlist connections into physical metal geometry without violating hundreds of foundry design rules. The flow is partitioned into:

  • Global Routing (GR): Partitions the die into Global Routing Cells (GRCs or tiles). It routes nets through tile boundaries without assigning exact tracks, estimating track capacity vs demand.
  • Track Assignment (TA): Assigns long straight net segments to specific routing tracks on preferred metal layers (horizontal on M2, M4, M6; vertical on M3, M5, M7).
  • Detailed Routing (DR): Resolves exact pin connections, via insertions, end-of-line (EOL) spacing, and enclosure rules using maze routing algorithms.
Antenna Violations (Plasma-Induced Gate Oxide Breakdown)
During reactive ion etching (RIE), long metal wires act as antennas, accumulating electrostatic charge. If connected directly to a thin transistor gate oxide without an alternative discharge path, the voltage punches through the gate dielectric, permanently destroying the transistor.

Fixes Claude evaluates:
1. Antenna Diode Insertion: Placing a reverse-biased diode connected between the net and VSS close to the victim gate pin to bleed charge harmlessly.
2. Layer Hopping (Jumper Insertion): Hopping the long interconnect up to a higher metal layer (e.g. M4 → M5 → M4) near the gate pin. During M4 etching, the long antenna segment is not yet physically connected to the gate.

Skill 06 Static Timing Analysis (STA): Setup, Hold, Recovery, Removal & Constraints

Static Timing Analysis verifies that every synchronous data path operates reliably under all process, voltage, and temperature (PVT) corners without requiring dynamic simulation testbenches. Claude parses PrimeTime, Tempus, or OpenSTA timing reports into clear component breakdowns.

Timing Check Mathematical Signoff Constraint Worst-Case Corner Primary Physical Fixes
Setup Timing (Max Delay) T_launch + T_ck2q + T_data ≤ T_clk + T_capture - T_setup - T_uncert Slow-Slow (SSG), Low Vdd, High/Low Temp Upsize cell, swap to LVT/SLVT, insert buffer to reduce slew, decompose logic.
Hold Timing (Min Delay) T_launch + T_ck2q + T_data ≥ T_capture + T_hold + T_uncert Fast-Fast (FFG), High Vdd, -40°C / 125°C Insert delay buffers (BUF_X1, DEL_X2) into data path near capture flip-flop.
Recovery Check Async reset deassertion must precede active clock edge by at least $T_{ ext{rec}}$. Slow Corner (SSG) Buffer reset distribution tree; balance reset arrival across registers.
Removal Check Async reset must remain asserted for at least $T_{ ext{rem}}$ after clock edge. Fast Corner (FFG) Delay reset assertion path; verify reset synchronizer topology.

Startpoint-to-Endpoint Path Breakdown: When inspecting an STA report, Claude calculates the Cell-to-Net Delay Ratio. If net delay exceeds 40%–50% of the total path delay, the path suffers from placement detours or high capacitive loading rather than excessive logic depth.

Skill 07 Timing Closure: Systematic Root-Cause Diagnosis & ECO Strategy

Timing closure is the iterative process of bringing Worst Negative Slack (WNS) and Total Negative Slack (TNS) to zero across all signoff modes and corners. Rather than blindly upsizing gates, a senior PD engineer applies systematic root-cause diagnosis:

scripts/sta/timing_eco_generation.tcl (Synopsys PrimeTime / Cadence Tempus) 
# PrimeTime Timing ECO Script: Precision Setup Slack Closure
# 1. Upsize high-fanout NAND gate driving critical ALU carry chain
size_cell u_core/u_alu/U_carry_gate_32 NAND2_X4

# 2. Swap critical-path multiplexer to Low-Vt (LVT) library variant
# Preserves footprint; reduces cell delay by ~28% with modest leakage trade-off
swap_cell u_core/u_alu/U_mux_result MUX2_X4_LVT

# 3. Buffer high-capacitance net traversing across core partition
insert_buffer u_core/u_alu/n_carry_overflow BUF_X8 -new_cell_name u_eco_buf_overflow_0

# 4. Save netlist changes for incremental back-annotation into PnR
write_changes -format eco_tcl -output reports/eco/primetime_eco_run03.tcl

Skill 08 Signal Integrity & Crosstalk: Miller Effect, Glitch Noise & SPEF Signoff

At sub-7nm geometries, wires are taller than they are wide (high aspect ratio). Consequently, coupling capacitance between neighboring wires ($C_{ ext{coupling}}$) accounts for up to 70%–80% of total interconnect capacitance.

  • Crosstalk Delay (Miller Effect): If an aggressor net switches in the opposite direction simultaneously with a victim net, effective capacitance doubles ($C_{ ext{eff}} pprox 2 \cdot C_c$), dramatically slowing the transition and causing setup violations. If they switch in the same direction, delay decreases ($C_{ ext{eff}} pprox 0$), inducing hold violations.
  • Crosstalk Noise (Glitch): When a victim net is steady (static 0 or 1), high $dv/dt$ on an adjacent aggressor injects a voltage pulse. If glitch height exceeds the receiving gate's noise margin ($V_{ ext{IL}}$ or $V_{ ext{IH}}$), false functional state transitions occur.
  • Why SPEF is Mandatory: Signoff tools cannot assess crosstalk without extracted Standard Parasitic Exchange Format (SPEF) containing explicit *C_COUP statements generated by 3D field solvers (StarRC or Quantus). Claude diagnoses coupling reports to recommend driver upsizing, net shielding, or track spacing.

Skill 09 Physical Verification: Calibre DRC, LVS, Antenna & DFM Metal Fill

Physical verification is the final gatekeeper before mask tapeout. Siemens Calibre (or Synopsys IC Validator) executes foundry rule decks covering:

Check Type Full Name What It Verifies Common Error Signatures
DRC Design Rule Checking Geometric manufacturing rules: min width, min spacing, via enclosure, end-of-line (EOL) spacing. M2.S.1 (spacing violation), VIA2.E.1 (insufficient enclosure).
LVS Layout Versus Schematic One-to-one equivalence between extracted layout netlist and synthesized schematic netlist. Unconnected pins (Opens), merged nets (Shorts), mismatched instance counts.
Antenna Process Antenna Rule Check Gate oxide area to metal collection area ratio. ANT.1 (ratio > 250:1 on poly/metal layers without diode).
Density / CMP Metal Density & Planarization Uniform metal and dielectric distribution across CMP polishing windows. Window under-density (< 20%) or over-density (> 70%) on M3/M4.

Skill 10 Engineering Change Orders (ECO): Functional, Timing & Metal-Only Spare Gates

When bugs or timing failures are discovered late in the cycle or after base wafer fabrication has begun, re-fabricating all mask layers costs upwards of $5M–$10M. A metal-only freeze-silicon ECO reconfigures pre-placed spare gate cells using only top metal layers (e.g. M2–M5), saving months of fabrication time and millions of dollars.

Claude assists backend teams by generating structured ECO scripts, verifying pin connection syntax, and parsing Conformal / Formality LEC reports to ensure non-ECO logic remains 100% equivalent.

Skill 11 Tcl Scripting & EDA Automation: Innovus, ICC2, PrimeTime & Python Parsers

Backend engineering productivity relies heavily on Tcl automation. Claude writes, debugs, and refines complex Tcl procedures for Innovus, ICC2, and PrimeTime, including custom timing path extractors, DRC report triage scripts, and automated CSV exporters.

Skill 12 Low-Power Physical Implementation: UPF 3.0, Power Switches & Isolation Cells

Modern SoCs employ Unified Power Format (IEEE 1801 / UPF 3.0) to define power management architectures with multiple voltage domains, dynamic voltage/frequency scaling (DVFS), and power-gated shutdown islands.

  • Power Switches: Header (PMOS) or footer (NMOS) MTCMOS sleep transistors that disconnect power from inactive blocks. Claude checks daisy-chain sleep signal sequencing to avoid peak inrush current.
  • Isolation Cells (ISO): Placed on signals leaving a power-gated domain to clamp outputs to known states (0 or 1), preventing floating inputs from causing crowbar current in always-on blocks.
  • Level Shifters (ELS): Bidirectional voltage converters placed at domain interfaces operating at different supply rails (e.g. 0.75V to 1.05V).
  • State Retention Flip-Flops (SRFF): Registers with low-leakage balloon latches powered by an always-on supply, saving critical state during sleep modes.

# Floorplan Review Skill for ASIC Physical Design

## Purpose
Performs architectural and physical evaluation of early floorplans, auditing core utilization, aspect ratio, macro orientations, channel spacing, power strap accessibility, and I/O pin feasibility to prevent downstream routing congestion and timing failure.

## When to Activate
Activate during initial die planning, after macro placement exploration, or when evaluating DEF / floorplan Tcl scripts before standard cell placement.

## Required Input Files
- Floorplan DEF (`.def`) or floorplan creation Tcl script (Innovus `create_floorplan` / ICC2 `initialize_floorplan`)
- Macro list and dimensions (SRAMs, ROMs, analog IP, PLLs)
- Top-level I/O pin constraint file or pin placement DEF
- Technology LEF / tech file (metal stack definition, track pitch)

## Step-by-Step Analysis Workflow
1. **Core Utilization & Aspect Ratio Audit:**
   - Verify core utilization ($	ext{Standard Cell Area} / 	ext{Core Area}$) is within target bounds (typically 65%–75% for advanced FinFET nodes).
   - Check aspect ratio ($H/W$) relative to package cavity, I/O ring requirements, and critical timing flylines.
2. **Macro Placement & Orientation Analysis:**
   - Verify macros are pushed toward the chip/block periphery, leaving a contiguous central core for standard cell placement.
   - Audit macro pin orientation: Ensure macro pins face the internal core, not the die boundary or adjacent macro walls.
   - Check macro spacing & halos: Ensure adequate channel width between macros ($W \ge 2 	imes 	ext{Power Strap Width} + 	ext{Routing Pitch}$) to prevent routing bottlenecks.
3. **Channel Congestion & Flyline Evaluation:**
   - Identify narrow channels between macro blocks that act as routing bottlenecks.
   - Check placement blockages (`create_placement_blockage -type hard/halo`) around macro boundaries.
4. **I/O Pin Placement & Power Ring Clearance:**
   - Verify pin distribution matches package bump / bond pad array.
   - Ensure pins are assigned to appropriate metal layers with legal track alignment.

## Tool-Specific Considerations
- **Cadence Innovus:** Uses `planDesign`, `createPlaceBlockage -type soft/hard/halo`, `assignIoPins`.
- **Synopsys ICC2:** Uses `initialize_floorplan -core_utilization`, `create_keepout_margin`, `set_block_pin_constraints`.

## Technical Limitations
- Visual floorplan inspection and script review cannot simulate global routing; always run Innovus `checkFPlan` or ICC2 `check_floorplan` to confirm zero overlaps and legal grid alignment.

## Output Format
- **Floorplan Metrics Scorecard:** Die Dimensions, Core Area, Utilization, Macro Count.
- **Identified Deficiencies & Bottlenecks:** Channel widths, pin orientations, blockage conflicts.
- **Refined Floorplan Tcl Commands:** Exact script fixes for Innovus or ICC2.
- **Validation Checklist:** Pre-placement readiness verification.

## Validation Checklist
- [ ] No macro-to-macro or macro-to-core boundary overlaps.
- [ ] Macro halos defined to prevent standard cell placement in tight channels.
- [ ] Routing tracks align with standard cell row grids.
- [ ] Core utilization accounts for routing and power mesh overhead.

[paste floorplan.tcl]

# Power Planning Review Skill

## Purpose
Analyzes ASIC Power Distribution Networks (PDN), verifying metal layer stack allocation, ring/stripe pitch, standard cell power rail connections, via arrays, and voltage domain isolation to prevent static IR drop and electromigration (EM) failures.

## When to Activate
Activate after macro placement and initial floorplanning, before standard cell placement, or when debugging power grid synthesis scripts.

## Required Input Files
- Power planning Tcl script (Innovus `addRing`, `addStripe` / ICC2 `create_pg_mesh`, `create_pg_std_cell_conn`)
- Technology LEF / Tech file (Metal layer sheet resistance $R_s$, max current density $J_{\max}$)
- Power domain specifications and supply voltages ($V_{DD}$, $V_{SS}$, multi-voltage rails)
- Early power budget estimates (Worst-case dynamic and leakage power)

## Step-by-Step Analysis Workflow
1. **Metal Stack Layer Allocation:**
   - Ensure top thick metals (e.g., M8/M9 or AP) carry global power distribution stripes to minimize $I \cdot R$ loss ($R_{	ext{thick}} \ll R_{	ext{thin}}$).
   - Verify intermediate metals (M4–M7) carry regional distribution stripes orthogonal to top metals.
   - Ensure bottom thin metal (M1) is strictly reserved for standard cell followpins/rails.
2. **Power Stripe Pitch & Width Calculation:**
   - Calculate stripe resistance: $R = R_s 	imes (L / W)$.
   - Verify grid density: Target PG metal utilization between 15% and 25% per routing layer to leave adequate tracks for signal routing.
3. **Standard Cell Rail & Via Array Integrity:**
   - Verify M1 rail width matches standard cell height pitch.
   - Confirm dense via arrays (stacked vias from top metal down to M1) are inserted at every orthogonal strap intersection.
4. **Power Domain & Voltage Area Isolation:**
   - Ensure separate power domains have independent PG meshes with dedicated boundary spacing.
   - Audit power switch cell (headswitch/footswitch) daisy chain and control grid connections.

## Tool-Specific Considerations
- **Cadence Innovus:** Uses `addRing`, `addStripe`, `sroute -connect {corePin padPin blockPin}`, `verifyPowerVia`.
- **Synopsys ICC2:** Uses `create_pg_mesh_pattern`, `set_pg_strategy`, `compile_pg`.

## Technical Limitations
- Claude cannot solve finite-element linear resistor matrices; quantitative static/dynamic IR drop and EM signoff require **Cadence Voltus** or **Synopsys RedHawk-SC**.

## Output Format
- **PDN Topology Summary:** Metal Layer | Direction | Width | Pitch | Resistance/um
- **Congestion vs IR Drop Assessment:** Trade-off analysis of PG blockage on signal routing.
- **Optimized Power Script:** Hardened Tcl script for grid construction.
- **Signoff Prerequisite Checklist:** Verification directives for Voltus / RedHawk.

## Validation Checklist
- [ ] Top metals carry primary global power currents.
- [ ] Via arrays placed at all strap intersections without DRC errors.
- [ ] Standard cell followpins continuously connected across rows.
- [ ] Sufficient routing resources remain for signal routing.

# Placement Optimization Review Skill

## Purpose
Inspects post-placement Quality of Results (QoR), evaluating cell density distributions, global routing congestion maps, setup timing WNS/TNS, high-fanout nets (HFN), and scan-chain ordering before clock tree synthesis.

## When to Activate
Activate immediately after global/detailed placement and pre-CTS timing optimization (`place_opt_design` / `place_opt`).

## Required Input Files
- Placement log file (Innovus `place_opt_design.log` / ICC2 `place_opt.log`)
- Pre-CTS timing summary report (`report_timing -max_paths 50`)
- Global routing congestion summary / GRC report
- High-fanout net report (`report_net -min_fanout 32`)

## Step-by-Step Analysis Workflow
1. **Placement Density & Spreading Audit:**
   - Check local density hotspots: Identify regions where standard cell density exceeds 85%, which triggers detailed routing DRC explosion.
   - Recommend density bounds (`set_placement_status`, `create_density_constraint`).
2. **Congestion-Driven Placement Check:**

# Setup Timing Debug Skill

## Purpose
Performs deep-dive engineering investigation of setup timing violations (max_delay), systematically deconstructing data arrival and required paths, logic depth, cell drive strengths, interconnect parasitics, and clock skew.

## When to Activate
Activate when analyzing post-placement, post-CTS, or post-route setup timing violations with negative slack.

## Required Input Files
- Full timing path report (`report_timing -nosplit -transition_time -capacitance -nets -attributes`)
- Target clock period and SDC constraints (`create_clock`, `set_clock_uncertainty`)
- Library operating corner (e.g., SSG 0.75V 125C worst-case setup corner)

## Step-by-Step Analysis Workflow
1. **Timing Path Topology Identification:**
   - Startpoint: Launch flip-flop, input port, or macro output.
   - Endpoint: Capture flip-flop data pin (D), output port, or macro input.
   - Launch & Capture clock domains and edge relationships (same-edge vs opposite-edge).
2. **Slack Equation Decomposition:**
   - $	ext{Slack} = 	ext{Data Required Time} - 	ext{Data Arrival Time}$.
   - $	ext{Data Arrival} = T_{	ext{launch\_latency}} + T_{	ext{CK}	o	ext{Q}} + T_{	ext{cell\_delay}} + T_{	ext{net\_delay}}$.
   - $	ext{Data Required} = T_{	ext{period}} + T_{	ext{capture\_latency}} - T_{	ext{setup}} - T_{	ext{uncertainty}}$.
3. **Bottleneck Component Isolation:**
   - **Cell vs Net Ratio:** Is delay dominated by cell switching (logic depth) or RC interconnect (long routing net / high capacitance)?
   - **Transition Violations:** Are cell delays inflated due to slow input slew rates?
   - **Drive Strength Sanity:** Are cells undersized (e.g., `X1` or `X2` driving long nets)?
   - **Clock Skew Effect:** Is clock skew hurting or helping slack?
4. **Remediation Strategy Formulation:**
   - Cell Sizing (`size_cell` to `X4`/`X8`).
   - Buffer Insertion (`insert_buffer` to split long resistive nets).
   - Logic Restructuring / Swapping to faster pin paths.
   - Useful Skew: Pushing capture clock latency later (if hold budget permits).

- **Cadence Tempus:** Uses `report_timing -late -view worst_setup`, `report_property`.

# Hold Timing Debug Skill

## Purpose
Investigates hold timing violations (min_delay), ensuring fast data paths cannot overwrite sequential flip-flop states before the required hold window elapses, prioritizing fixes at fast PVT corners.

## When to Activate
Activate during post-CTS and post-route timing closure, specifically when running STA on fast/hold corners (e.g., FFG 0.88V -40C).

- SDC hold uncertainty constraints (`set_clock_uncertainty -hold`)

## Step-by-Step Analysis Workflow
1. **Hold Equation Decomposition:**
   - $	ext{Slack}_{	ext{hold}} = 	ext{Data Arrival Time} - 	ext{Data Required Time}$.
   - $	ext{Data Arrival} = T_{	ext{launch\_latency}} + T_{	ext{CK}	o	ext{Q}} + T_{	ext{combinational\_min}}$.

# IR Drop & Electromigration (EM) Analysis Skill

## Purpose
Interprets static and dynamic IR drop distributions and signal/power electromigration (EM) reports from signoff power analysis tools (Cadence Voltus, Synopsys RedHawk-SC), identifying power grid starvation and high-current hotspots.

## When to Activate
Activate during post-CTS and post-route power integrity signoff, or when diagnosing voltage drop induced timing failures.

## Required Input Files
- IR drop summary report (Voltus `report_ir_drop` / RedHawk `static_ir_summary`)
- Vectorless or VCD-driven dynamic power analysis configuration
- Supply voltage specifications and allowable drop threshold (e.g., $V_{	ext{drop}} \le 5\% 	imes V_{DD}$)

## Step-by-Step Analysis Workflow
1. **Static vs Dynamic IR Drop Classification:**
   - Static IR Drop: Caused by average DC current flowing through power grid resistance ($V = I_{	ext{avg}} \cdot R_{	ext{grid}}$). Indicates inadequate power straps or missing vias.
   - Dynamic IR Drop: Caused by instantaneous simultaneous switching current ($L \cdot di/dt + I_{	ext{peak}} \cdot R$). Indicates simultaneous clock tree buffer switching or high-activity datapath clusters.
2. **Power Mesh Resistance Mapping:**
   - Trace IR drop contours back to power pad / bump locations. Identify regions far from power bumps with high effective resistance ($R_{	ext{eff}}$).
3. **Electromigration (EM) Violation Audit:**
   - Signal EM: High-frequency clock nets driving high capacitive loads exceeding metal current density limits ($J_{	ext{rms}}, J_{	ext{avg}}$).
   - Power EM: Power stripes feeding large standard cell blocks carrying current exceeding electromigration lifespan thresholds.
4. **Remediation Plan:**
   - Static Fix: Add intermediate power stripes or increase via array density.
   - Dynamic Fix: Insert Decoupling Capacitance (Decap) standard cells adjacent to switching hotspots; stagger clock tree buffer trigger edges.

## Tool-Specific Considerations
- **Cadence Voltus:** Native signoff power integrity solution.
- **Synopsys RedHawk-SC:** Industry standard grid and dynamic IR signoff engine.

## Technical Limitations
- IR drop is highly sensitive to switching activity vectors; vectorless analysis is conservative, while VCD analysis depends strictly on testbench stimulus realism.

## Output Format
- **Power Integrity Scorecard:** Worst Static Drop (mV), Worst Dynamic Drop (mV), EM Violating Nets Count.
- **Hotspot Location Diagnosis:** Correlation with standard cell density and clock buffer trees.
- **Actionable Remediation Prescription:** Decap cell insertion guidelines and power strap reinforcement.

Project E Automating Static Timing Report Analysis with Python & Tcl

scripts/automation/parse_primetime_report.py
import re
import sys

def parse_pt_timing_report(file_path):
    with open(file_path, "r", encoding="utf-8") as f:
        content = f.read()

    paths = content.split("Startpoint:")
    parsed_paths = []

    for p in paths[1:]:
        p = "Startpoint:" + p
        startpoint = re.search(r"Startpoint:\s+([^\s\(\)]+)", p)
        endpoint   = re.search(r"Endpoint:\s+([^\s\(\)]+)", p)
        slack      = re.search(r"slack\s+\((VIOLATED|MET)\)\s+([-\d\.]+)", p)
        
        # Calculate cell vs net delays
        net_delays = sum(float(x) for x in re.findall(r"\(net[^\)]*\)\s+([\d\.]+)", p))
        total_data = re.search(r"data arrival time\s+([\d\.]+)", p)

        if startpoint and endpoint and slack:
            s_name = startpoint.group(1)
            e_name = endpoint.group(1)
            status = slack.group(1)
            val    = float(slack.group(2))
            t_data = float(total_data.group(1)) if total_data else 1.0
            net_pct = (net_delays / t_data) * 100 if t_data > 0 else 0

            parsed_paths.append({
                "start": s_name, "end": e_name, "status": status,
                "slack": val, "net_pct": round(net_pct, 1)
            })

    print("| Rank | Slack (ns) | Net Delay % | Bottleneck Endpoint | Diagnosis |")
    print("|---|---|---|---|---|")
    sorted_paths = sorted(parsed_paths, key=lambda x: x["slack"])
    for idx, path in enumerate(sorted_paths[:10], 1):
        diag = "Net Detour / Fanout" if path["net_pct"] > 45 else "Deep Logic Levels"
        print(f"| {idx} | {path['slack']:.3f} | {path['net_pct']}% | `{path['end']}` | {diag} |")

if __name__ == "__main__":
    if len(sys.argv) > 1:
        parse_pt_timing_report(sys.argv[1])
    else:
        print("Usage: python parse_primetime_report.py ")

Output Format: Automatically flags whether the path bottleneck is due to high interconnect routing resistance/capacitance (> 45% net delay) or excessive combinational gate depth.

Chapter 8 · Tapeout Security

Security, Intellectual Property & Production Design Safety

Protecting Semiconductor IP in the Age of Generative AI

Semiconductor physical design assets — including standard cell Liberty models (.lib), LEF footprint definitions, proprietary layout DEF files, GDSII stream data, and signoff SDC constraints — represent tens of millions of dollars in corporate R&D and strict foundry Non-Disclosure Agreements (NDAs).

Critical Security Prohibitions
  • Never upload raw GDSII / OASIS stream files: GDSII contains actual transistor layout geometries and foundry layer numbers. Uploading GDSII to public AI platforms violates foundry legal NDAs.
  • Never upload Liberty (.lib) lookup tables: Standard cell timing libraries contain proprietary SPICE-characterized non-linear delay tables belonging to ARM, Synopsys, or foundries.
  • Mandate Enterprise Zero Data Retention (ZDR): Backend engineering teams must operate exclusively on private cloud or enterprise AI contracts where prompts and logs are not retained for model training.

import re

def sanitize_report(input_text):
    # Anonymize proprietary block and instance paths
    text = re.sub(r'u_secret_crypto_core_\w+', 'u_block_alpha', input_text)
    text = re.sub(r'u_neural_npu_\w+', 'u_compute_core', text)
    # Mask specific foundry cell library names
    text = re.sub(r'TSMC\w+_SVTLOW', 'STD_CELL_SVT', text)
    text = re.sub(r'GF\w+_LVT', 'STD_CELL_LVT', text)
    # Remove absolute Linux file system paths
    text = re.sub(r'/proj/[^/]+/[^/]+/', '/workspace/asic_run/', text)
    return text

Physical Design & AI Engineering FAQ

1. Can Claude directly perform place and route or run signoff timing closure?

No. Claude is an LLM with no internal spatial solvers, no 3D field extraction engine, and no non-linear delay calculators. It cannot route metal wires or close timing independently. Claude serves as an expert diagnostic assistant that analyzes reports, identifies physical bottlenecks, generates verified Tcl scripts, and assists engineers in directing commercial EDA tools (Innovus, ICC2, PrimeTime).

2. How does Claude assist with floorplan optimization and macro placement?

Claude reviews floorplan DEF parameters, die dimensions, and macro aspect ratios to identify channel starvation bottlenecks, flyline crossing density between SRAM banks and top-level I/O pins, inadequate power strap spacing, and missing halo keepouts. It outputs structured Tcl commands (e.g. createPlaceBlockage, set_keepout_margin) to resolve routing blockages before cell placement begins.

3. Can Claude diagnose complex setup and hold timing violations in PrimeTime or Tempus?

Yes. When provided with a detailed STA timing report, Claude parses the data path breakdown: separating launch clock latency, CK-to-Q delay, combinational cell delays, interconnect net delays, capture clock latency, and clock uncertainty. It computes cell-versus-net delay ratios, flags deep logic cascades, identifies high-fanout or detoured nets, checks for missing useful skew or threshold voltage (Vt) swapping opportunities, and generates precision ECO Tcl scripts.

4. What is the difference between global clock skew and local clock skew, and how does Claude evaluate them?

Global skew is the maximum latency difference between any two clock endpoints across the entire die, whereas local skew is the latency difference between physically or logically communicating flip-flop pairs. Claude evaluates CTS summary reports to confirm that while global skew may be bounded (e.g. < 250 ps), local skew between synchronous launch and capture registers meets the tight hold timing budget (< 50 ps), preventing hold buffers from consuming excessive dynamic power and routing tracks.

5. How does Claude handle Calibre DRC and LVS reports without viewing graphical GDSII layouts?

Claude parses textual Calibre DRC summary and error transcript files (.sum / .drc.results), categorizing violations by rule name (e.g., MinSpacing, MinWidth, Enclosure, Antenna ratio, Via enclosure). It identifies localized clustering hotspots by coordinate distribution, maps violations back to root causes (such as dense pin routing, missing metal fill, or layer transition bottlenecks), and generates targeted router search-and-repair Tcl commands.

6. Is it safe to share proprietary ASIC floorplans, DEF files, and LEF libraries with Claude?

Proprietary physical design databases (GDSII, LEF, DEF, SPEF, .lib) contain company trade secrets and foundry NDAs. Backend teams must never paste raw IP into public AI portals. Safe workflows require enterprise Claude instances under Zero Data Retention (ZDR) agreements, self-hosted private endpoints, or automated sanitization scripts that strip proprietary instance names, cell library vendor identifiers, and coordinate offsets before LLM prompt submission.

7. What are the 15 Claude Code Physical Design skills provided in this guide?

The 15 skills are standardized, version-controlled SKILL.md packages covering: floorplan review, power planning review, placement optimization, CTS report analysis, routing congestion triage, setup timing debug, hold timing debug, STA report analysis, timing constraint review, Tcl script debugging, DRC violation triage, LVS debug assistance, IR drop and EM analysis, ECO review, and physical design run-to-run comparison.

8. How does Claude help with static and dynamic IR drop analysis?

Claude analyzes Voltus and RedHawk-SC summary reports, identifying power mesh weaknesses, insufficient via arrays between top metal straps and standard cell rails, excessive localized cell switching density, and high dynamic toggle rates. It recommends power strap widening, strap pitch reduction, decap cell insertion, and clock gate de-synchronization to resolve supply bounce.
