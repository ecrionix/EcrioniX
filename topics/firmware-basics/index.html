What Does Firmware Do? Deep Dive with Simulation Example

By EcrioniX · 24 Sep 2026 · ~7 min read

Firmware is the thin layer of code that lives in non‑volatile memory on a microcontroller, bridging the raw silicon to high‑level software. It boots the chip, configures peripherals, and runs the real‑time tasks that make your IoT device functional. Below we unpack the entire lifecycle and provide a concrete simulation of a blinking‑LED firmware, visualized with WaveDrom.

1. Firmware Lifecycle Overview

At a high level, firmware follows these phases:

  1. Reset & Power‑On – The microcontroller’s reset circuitry pulls the PC (program counter) to the vector table start address.
  2. Bootloader (optional) – A minimal piece of code that can verify integrity, select an application image, or perform an OTA update.
  3. System Init – Clock configuration, peripheral enable, memory initialization (zero‑init .bss, copy .data from flash to RAM).
  4. Main Application Loop – The infinite while(1) loop that drives tasks, handles interrupts, and schedules RTOS threads.

2. Minimal Firmware Example (C)

#include <stdint.h>
#define LED_PORT   (*(volatile uint32_t*)0x40021018) // GPIOB ODR address (example)
#define LED_PIN    (1U << 5) // PB5

void delay_ms(uint32_t ms) {
    // Naïve busy‑wait – in real silicon this maps to a timer peripheral.
    for (volatile uint32_t i = 0; i < ms * 8000U; ++i) {
        __asm__("nop");
    }
}

int main(void) {
    // 1. Enable GPIO B clock (implementation‑specific, omitted here)
    // 2. Set LED pin as output (omitted)    
    while (1) {
        LED_PORT ^= LED_PIN;   // toggle LED
        delay_ms(500);         // 500 ms half‑period → 1 Hz blink
    }
    return 0; // never reached
}

Even though the code is tiny, the firmware does three critical things:

  • Directly manipulates hardware registers (the LED port address).
  • Implements a deterministic timing loop (the busy‑wait mimics a timer peripheral).
  • Runs forever – the infinite loop is the heart of an embedded system.

4. Why Firmware Needs a Dedicated Layer

Determinism: Firmware runs without an OS, so every instruction must have a known execution time. This is why busy‑wait loops or hardware timers are used – they provide a predictable temporal budget.

Resource Constraints: Memory footprints are often measured in a few kilobytes. The example above fits in ~1 KB of flash and <10 B of RAM.

Safety & Security: The bootloader can cryptographically verify the main application before jumping, ensuring only trusted firmware runs on the device.

5. Extending the Simulation (Verilog Testbench)

If you want to test the firmware in a pure RTL environment, you can write a simple SystemVerilog testbench that models the CPU's fetch‑decode‑execute cycle. Below is a snippet that drives the same LED toggle logic in a simulated microcontroller model.

`timescale 1ns/1ps
module fw_tb;
  reg clk = 0;
  reg rst = 1;
  wire led;

  // Simple CPU model: only PC and toggle instruction
  reg [7:0] pc = 0;
  reg led_reg = 0;
  assign led = led_reg;

  // Clock = 10 ns period (100 MHz)
  always #5 clk = ~clk;

  // Reset release after 30 ns
  initial begin
    #30 rst = 0;
  end

  // Fetch‑Decode‑Execute (one instruction per clock)
  always @(posedge clk) begin
    if (rst) begin
      pc <= 0; led_reg <= 0;
    end else begin
      case (pc)
        8'h00: pc <= pc + 1; // NOP
        8'h01: begin pc <= pc + 1; end // NOP
        8'h02: begin led_reg <= ~led_reg; pc <= pc + 1; end // TOGGLE LED
        default: pc <= pc + 1;
      endcase
    end
  end

  // End simulation after 200 cycles
  initial begin
    #2000 $finish;
  end

  // Dump waveform
  initial begin
    $dumpfile("fw_tb.vcd");
    $dumpvars(0, fw_tb);
  end
endmodule

This testbench produces a waveform (`fw_tb.vcd`) that you can view with any VCD viewer – you will see the same square‑wave LED pattern as the WaveDrom diagram above.

6. FAQ – Firmware in the Real World

Q: Does firmware run on the CPU or on a separate co‑processor?

A: In most microcontrollers the firmware runs on the core CPU (ARM Cortex‑M, RISC‑V, etc.). Some SoCs have a dedicated “management engine” (e.g., Intel ME) that runs its own firmware, but for typical embedded designs the same core executes the bootloader and main application.

Q: How do I update firmware safely?

A: Implement a dual‑bank flash layout. The bootloader validates a new image via a cryptographic hash before flipping a flag that tells the boot logic which bank to boot from. If verification fails, it stays on the known‑good bank.

Q: Can I run an OS on top of firmware?

A: Yes. Firmware can start a lightweight RTOS (FreeRTOS, Zephyr) after hardware init. The RTOS then schedules tasks, but the underlying bootloader and init code remain firmware.
