The CDC Reconvergence Problem

By EcrioniX · 24 Sep 2026 · ~14 min read

You've learned the golden rule of CDC: pass a single-bit signal through a 2-flop synchronizer. But what happens when you need to pass two or more related signals across the clock boundary? If you give each signal its own synchronizer, you've just created one of the most dangerous bugs in all of silicon engineering: CDC Reconvergence.

1. Quick Recap: The 2-Flop Synchronizer

When a signal crosses from Clock Domain A (the source) to Clock Domain B (the destination), it may violate the destination flip-flop's setup/hold time. This puts the flop into metastability — the output voltage hovers at an invalid level between 0 and 1.

The industry-standard fix is the 2-flop synchronizer. Two flip-flops are chained together in the destination domain. The first flop may go metastable, but it has an entire clock period to resolve. The second flop then captures a clean, valid 0 or 1.

The standard 2-flop synchronizer. FF1 absorbs metastability; FF2 outputs a clean value.

This is bulletproof for a single bit. But the moment you need to synchronize two or more related bits, a subtle and devastating problem emerges.

2. The 1-Cycle Uncertainty

A 2-flop synchronizer does not guarantee which clock cycle the signal will be captured on. Because the TX and RX clocks are asynchronous, the TX signal might arrive a picosecond before the RX clock edge, or a picosecond after it.

This means every synchronizer has a ±1 cycle uncertainty window. For a single bit this is harmless — you just see the new value one cycle earlier or later. But for two bits going through separate synchronizers…

The Critical Insight

Two signals arriving at the same time at the destination domain can be captured on different clock edges by their respective synchronizers. One synchronizer barely catches the new value; the other barely misses it and delays by one cycle. The outputs are now misaligned.

3. The Reconvergence Disaster: Phantom States

Let's walk through the exact failure scenario. You have a state machine in Clock Domain A that outputs a 2-bit state {A, B}. The state transitions from 00 → 11 (both bits flip simultaneously).

You need to observe this state in Clock Domain B. So you instantiate two separate 2-flop synchronizers — one for bit A, one for bit B — and combine their outputs in the destination logic.

The reconvergence bug: Two separate synchronizers feed into combinational logic. Their outputs can be misaligned by one cycle.

Now here is the exact failure, cycle by cycle:

💀 The Phantom State: 10

For one entire clock cycle, the destination domain sees RX_A=1, RX_B=0. The state 10 never existed in Clock Domain A. The source went directly from 00 to 11. But the destination sees an impossible intermediate state.

If this phantom state triggers a state machine transition, clears a register, or asserts an interrupt — your chip has a functional silicon failure that only appears randomly in the field. Good luck debugging that.

This problem is called reconvergence because the two synchronizer paths reconverge (come back together) at the combinational logic gate in the destination domain. Each path independently has a 1-cycle uncertainty, and the logic gate sees the misaligned result.

4. Fix #1: Gray Code (For Counters & Pointers)

If the multi-bit signal you need to cross is a counter (like the read/write pointer in an asynchronous FIFO), you can encode it in Gray Code before crossing the boundary.

In Gray Code, only one bit changes per increment. If only one bit flips, there is only one synchronizer involved in the transition, so there is no multi-path skew — no phantom state is possible.

DecimalBinaryGray CodeBits Changed
0000000—
10010011 bit ✅
20100111 bit ✅

41001101 bit ✅

Compare this to binary: going from 011 to 100 (3 → 4) flips all three bits. That is three separate synchronizers racing — a perfect storm for phantom states. Gray Code avoids this entirely.

binary_to_gray.v
// Binary to Gray conversion — one XOR gate per bit
assign gray = binary ^ (binary >> 1);

// Gray to Binary conversion (at the destination)
assign binary[N-1] = gray[N-1];
genvar i;
generate
  for (i = N-2; i >= 0; i = i-1) begin
    assign binary[i] = binary[i+1] ^ gray[i];
  end
endgenerate

Where You See Gray Code in the Wild

Every asynchronous FIFO in every chip you've ever used (your phone's SoC, your laptop's PCIe controller, your SSD's NAND interface) uses Gray-coded read/write pointers to safely cross the FIFO's dual clock domains. It is the single most important application of Gray Code in digital design.

5. Fix #2: Synchronized Valid Flag (Arbitrary Data)

Gray Code only works for counters (values that increment by 1). What if you need to cross an arbitrary 32-bit data bus where any bits can change at any time?

The answer is to never synchronize the data bus itself. Instead, use a single-bit valid flag as the gatekeeper.

The data bus crosses unsynchronized. Only the 1-bit valid flag goes through a 2-flop synchronizer. The destination register only captures data when synced_valid rises.

The protocol works like this:

  1. The source domain places stable data on the bus and holds it steady.
  2. After the data has settled (at least one source clock cycle), the source asserts valid = 1.
  3. The valid signal passes through a 2-flop synchronizer into the destination domain (2–3 destination clock cycles of latency).
  4. When the synchronized valid arrives as a 1 in the destination, the data bus has been stable for several destination clock cycles. The destination safely latches it.

Why This Works

Only one bit (the valid flag) crosses through a synchronizer, so there is zero reconvergence risk. The multi-bit data bus is never synchronized — it is simply held stable long enough that by the time the valid flag arrives, every data bit has definitively settled to its correct value in the destination domain's flip-flops.

6. Fix #3: Pre-CDC Logic Merging

Sometimes the simplest fix is the best. If you have two flags that both need to cross the domain — like irq_a and irq_b — and they feed into a single AND gate in the destination, move the AND gate into the source domain.

Left: Two separate synchronizers reconverge at an AND gate — BUG. Right: AND gate moved to source domain, single synchronizer — SAFE.

Rule of thumb: Always reduce signals in the source domain before crossing whenever possible. The fewer signals you cross, the fewer reconvergence paths you can accidentally create.

7. Fix #4: Asynchronous FIFO (Streaming Data)

When you need to continuously stream multi-bit data across clock domains (not just a single transfer), neither the valid-flag handshake nor Gray Code alone is sufficient. The industry-standard solution is the Asynchronous FIFO (Dual-Clock FIFO).

An async FIFO is a small dual-port RAM with:

  • A write pointer clocked by the source domain (clk_a).
  • A read pointer clocked by the destination domain (clk_b).
  • Both pointers are Gray-coded and crossed into the opposite domain to determine full/empty status.
Async FIFO architecture: Gray-coded pointers cross domains via 2-flop synchronizers. Data flows through dual-port RAM without synchronizers.

Why Async FIFOs Are Safe

The data bus is read directly from the RAM — no synchronizers. The only signals crossing clock domains are the Gray-coded pointers (one bit changes at a time). The full/empty flags are computed from the synchronized pointers, so they may be slightly "pessimistic" (declaring full when there's still one slot, or empty when there's still one entry), but they are never wrong in a dangerous direction.

8. How CDC Lint Tools Catch This

In the real ASIC industry, no one relies on manual code review to catch reconvergence. Teams run specialized CDC lint tools that structurally analyze the netlist:

ToolVendorWhat It Does
Spyglass CDCSynopsysTraces all multi-bit paths through synchronizers and flags any that reconverge in the destination domain.
Meridian CDCCadenceBuilds a "convergence graph" showing exactly which synchronized signals feed into the same logic cone.
Questa CDCSiemens EDAProtocol-aware CDC verification with formal proof that no phantom state can reach an observable output.

These tools typically report reconvergence as a high-severity violation. The report looks something like:

spyglass_cdc_report.rpt
ERROR [CDC-RECONV-01] Reconvergence detected!
  Source signals: tx_state[0], tx_state[1]
  Sync paths:
    tx_state[0] → sync_a_ff1 → sync_a_ff2 → dest_logic/U42
    tx_state[1] → sync_b_ff1 → sync_b_ff2 → dest_logic/U42
  Reconvergence point: dest_logic/U42 (AND2)
  Severity: HIGH — Phantom state possible

If you see this in your CDC report, you must restructure the crossing using one of the four fixes described above. You cannot waive this violation — it represents a real silicon risk.

9. Summary & Key Rules

Key Takeaways

  • Never pass multiple related signals through separate synchronizers and combine them in the destination.
  • Synchronizers have a 1-cycle uncertainty. Two synchronizers will not output aligned signals at the same time.
  • Use Gray Code for counters and pointers (only 1 bit changes per increment).
  • Use a synchronized valid flag to gate the capture of unsynchronized multi-bit data buses.
  • Merge logic before crossing — reduce the number of bits that need to cross the domain.
  • For streaming data, use an Async FIFO (dual-clock FIFO with Gray-coded pointers).
  • Always run a CDC lint tool (Spyglass CDC, Meridian CDC, Questa CDC) before tapeout.
