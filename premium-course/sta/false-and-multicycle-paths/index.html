False Paths & Multicycle Paths

Module 3, Lesson 1 • EcrioniX STA Premium Course

In standard Static Timing Analysis (STA), the timing engine assumes that data launched from a flip-flop on one clock edge must be captured by the destination flip-flop on the very next clock edge. However, real-world designs often exhibit behaviors that violate this strict 1-cycle assumption. To prevent the STA engine from unnecessarily optimizing these paths—or reporting false violations—we use Timing Exceptions.

The two most critical timing exceptions every Silicon Engineer must master are False Paths and Multicycle Paths (MCPs).

1. False Paths

What is a False Path?

A False Path is a topological path in the design that exists structurally, but will never be sensitized or used during actual operation in a way that requires timing closure. Since data never legitimately flows through this path, any timing violation reported on it is "false."

Common Scenarios for False Paths

  • Static Logic: Paths driven by static configuration registers. Once the system boots, these registers hold a constant value, so there is no active switching during normal operation.
  • Logically Impossible Paths: Paths gated by mutually exclusive multiplexer select lines where the hardware cannot physically route the logic concurrently.
  • Crossing Asynchronous Domains: Paths between two clock domains that have no known phase relationship (e.g., crossing from a 100MHz clock to an unaligned 133MHz clock). Instead of standard setup/hold checks, these paths must be handled using robust structural synchronizers (like a 2-flop synchronizer or async FIFO), making synchronous STA rules irrelevant.

Why do we use set_false_path?

If we don't explicitly declare these paths as false, the STA tool will waste significant computational resources, silicon area, and power trying to optimize them. It might try to insert buffers or upsize cells to fix a setup violation on a path that is impossible to trigger. Applying set_false_path safely removes these paths from the timing graph.

# Ignore paths crossing from the APB clock domain to the AXI clock domain set_false_path -from [get_clocks clk_apb] -to [get_clocks clk_axi] # Ignore timing through static configuration registers set_false_path -through [get_pins u_config_reg/Q]
2. Multicycle Paths (MCP)

What is a Multicycle Path?

A Multicycle Path (MCP) is a path where data is intentionally designed to take more than one clock cycle to propagate from the launch register to the capture register. This is a common architectural decision in complex arithmetic operations (like MAC units or heavy crypto pipelines) where the combinatorial logic depth is simply too large to fit in a single clock period, and deep pipelining is constrained.

Why do we use set_multicycle_path?

By default, STA enforces a 1-cycle requirement for the setup check. If your combinational logic takes 1.5 cycles, STA will report a massive setup violation. By using set_multicycle_path, we relax the setup constraint to N cycles, allowing the data enough time to arrive naturally without forcing the synthesis tool to aggressively insert low-Vt (high leakage) cells to crunch the logic into 1 cycle.

The Setup and Hold Relationship (The Tricky Part)

When you define a Multicycle Path of 2 cycles, you shift the Setup Capture Edge forward by 1 cycle (from edge 1 to edge 2). However, in industry STA engines, moving the setup edge automatically shifts the Hold Check Edge forward as well (to one cycle before the new setup edge, which is edge 1). This default behavior is almost never what you want in silicon design!

Crucial STA Rule: In an MCP where data takes 2 cycles to propagate, the launch register is usually only updated every 2 cycles (often via a clock enable). Therefore, you must hold the data against the original launch edge (edge 0). You must explicitly bring the hold check back to edge 0 using -hold 1.
# 1. Relax the Setup check to 2 cycles set_multicycle_path -setup 2 -from [get_pins launch_reg/Q] -to [get_pins capture_reg/D] # 2. Shift the Hold check back by 1 cycle (back to the launch edge) set_multicycle_path -hold 1 -from [get_pins launch_reg/Q] -to [get_pins capture_reg/D]
3. Visualizing Setup and Hold on an MCP

The WaveDrom diagram below illustrates exactly how applying an MCP of 2 cycles affects the edges used for setup and hold timing checks.

Breaking down the timeline:

  • Launch Edge (L): Data is launched out of the driving flip-flop at clock cycle 0.
  • Default Setup (s): By default, STA checks setup at cycle 1.
  • MCP Setup (S): Applying -setup 2 correctly moves the capture edge to cycle 2, giving the data more time to propagate through the deep combinational logic.
  • Default Hold for MCP (H): STA automatically moves the hold check to cycle 1. If left uncorrected, fast paths might violate hold against this new edge!
  • Corrected Hold (R): Applying -hold 1 pulls the hold check safely back to cycle 0, ensuring short paths don't trample the previous data.
