Lesson 4.5

Clock Uncertainty

Clock uncertainty is the single SDC knob that bundles every source of unpredictable clock-edge timing error — jitter, unmodeled skew, margin for early-stage estimation — into one number the STA engine subtracts from every timing check. Getting it right (and understanding what it is quietly hiding) is one of the most consequential decisions an STA engineer makes.

1. The SDC command and its two faces
set_clock_uncertainty -setup 0.090 [get_clocks CLK] set_clock_uncertainty -hold 0.025 [get_clocks CLK] # or, applied uniformly without direction: set_clock_uncertainty 0.060 [get_clocks CLK]

set_clock_uncertainty tells the STA tool: "subtract this much extra margin from every path using this clock, on top of whatever the timing graph already computes." It is applied as a straight subtraction at the capture point of every path — conceptually, the tool pretends the capture clock edge is slightly less favorable than the propagated clock network delay alone would suggest.

Separate -setup and -hold values exist because the physical phenomena that make setup and hold risky are not identical in magnitude (see Lesson 4.3 on jitter) — setup uncertainty is almost always the larger number because it must cover a full period's worth of jitter and pessimism, while hold uncertainty covers only the same-edge race window.

2. What actually goes into the uncertainty number

3. Pre-CTS vs. post-CTS uncertainty — a critical distinction

This is where many new STA engineers get confused, because the "right" uncertainty value changes dramatically across the design flow:

  • Pre-CTS (RTL synthesis, floorplan-stage STA): the clock tree does not exist yet — every flop is assumed to receive the clock from an ideal, zero-skew source. Because real skew will appear later and cannot yet be predicted, engineers apply a large, conservative uncertainty (often 150-250ps for a ~1GHz design) purely as a placeholder for "skew we haven't built yet." This prevents synthesis from over-optimizing a critical path that will turn out to have real skew margin once CTS runs.
  • Post-CTS (after clock tree synthesis, place & route): real skew is now visible directly in the timing graph via the propagated clock network delay difference between launch and capture (Lesson 4.2). The uncertainty value is reduced to reflect only the genuinely unmodeled residual: jitter, CRPR residual, and small OCV-related derating not already covered by the AOCV/POCV model. Typical post-CTS uncertainty is much smaller — often 30-80ps for the same 1GHz design.
Common flow bug: forgetting to shrink clock uncertainty after CTS. This leaves two full skew estimates stacked on top of each other — the real, propagated skew from the built clock tree, plus the old pre-CTS placeholder still counted as if the tree didn't exist. The result is a design that looks like it has a much worse (or better, in unlucky cases) timing margin than it actually does, and can send the physical design team chasing paths that were never actually critical.
4. Uncertainty vs. explicitly modeling skew and jitter separately

A natural question: why not just model real skew directly (from the propagated clock tree) and real jitter directly (from PLL characterization), and skip the blanket uncertainty margin entirely? In fact, mature flows do exactly this for skew — post-CTS STA uses the real, propagated clock latency values, so skew is not double-counted through uncertainty; only the residual (jitter + CRPR residual) remains in the uncertainty term.

Jitter, however, is fundamentally different: it is a statistical, time-varying quantity that cannot be "propagated" through a static timing graph the way a fixed wire delay can. There is no meaningful single-number "jitter delay" to place on a specific net the way there is for skew. This is precisely why jitter must remain in the uncertainty bucket permanently, at every stage of the flow, while skew's contribution to uncertainty shrinks toward zero as the clock tree becomes real.

5. Uncertainty in a timing report
clock CLK (rise edge) 1.00 1.00 clock network delay (propagated) 0.71 1.71 clock reconvergence pessimism 0.00 1.71 clock uncertainty -0.06 1.65 <- set_clock_uncertainty applied here reg_B/CP 1.65 r library setup time -0.09 1.56 data required time 1.56

The uncertainty line appears as a direct subtraction on the required-time side of the report, right after clock reconvergence pessimism removal (CRPR) and before the library setup/hold time itself is applied. This ordering matters: uncertainty is subtracted from an already-CRPR-corrected required time, so it is not compensating for common-path pessimism (CRPR's job) — it is purely covering the genuinely unmodeled, unpredictable residual described above.

6. Getting the number wrong: both directions are costly
MistakeConsequence
Uncertainty set too highSynthesis/PnR over-constrains the design, burning area and power upsizing cells and buffering paths that were never actually going to fail in silicon — wasted PPA (power, performance, area) budget.
Uncertainty set too lowDesign "closes" in STA reports but fails in real silicon due to jitter or margin the model never accounted for — the single most dangerous class of STA methodology error because it produces false confidence.

Because of this asymmetry, most signoff methodologies deliberately err toward slightly conservative uncertainty values, then work to recover PPA loss through targeted, per-path exceptions rather than by shrinking the global uncertainty number.
