STA / Module 4: Advanced Clocking
Lesson 4.8

Multiplexed Clocks

Many SoCs run a given clock domain from one of several possible clock sources — a fast PLL output during normal operation, a slow reference oscillator during power-up, a test clock during scan. Selecting between them with an ordinary combinational MUX on the clock net is one of the most dangerous constructs in digital design, and STA needs explicit help to time it at all.

1. The problem: STA must analyze every mux selection, not just the active one

A clock select MUX has, from STA's point of view, multiple input clocks converging on one output net that then fans out to feed real flops. Every one of those input clocks is a legitimate, independently-timed clock (different frequency, different source latency, different jitter), and — critically — STA by default has no way to know which select value corresponds to real, reachable silicon behavior. Left unconstrained, the tool will attempt to analyze the mux output as if all input clocks could somehow be simultaneously active, producing a combinatorial explosion of nonsensical clock relationships and false violations.

2. Two SDC strategies: case_analysis vs. explicit multi-mode scenarios
ApproachHow it worksWhen to use it
set_case_analysisFixes the mux select pin to a constant 0 or 1 for a given STA run, collapsing the mux to a single active input for that analysis — the tool propagates only the selected clock and ignores the others entirely for this scenarioSimple designs with 2-3 clock sources and only a couple of relevant operating modes; quick to set up
MMMC scenarios (create_scenario)Each possible clock-select state becomes its own full scenario/view with its own case_analysis setting underneath, all analyzed together as part of signoff (see Lesson 3.5 on MMMC)Real SoCs with many clock domains and multiple legal select combinations that must all be verified for full coverage before tapeout
# Scenario A: run from PLL clock, select = 1 set_case_analysis 1 [get_pins u_clkmux/SEL] create_clock -name CLK_PLL -period 1.0 [get_pins u_pll/CLK_OUT] # Scenario B: run from reference oscillator, select = 0 set_case_analysis 0 [get_pins u_clkmux/SEL] create_clock -name CLK_REF -period 20.0 [get_pins u_refosc/CLK_OUT]

Both scenarios must be run and must pass independently — a design that only closes timing when the select pin happens to be fixed one way is not actually verified for the other legal operating mode.

3. The physical danger: glitches during a live clock switch

Everything above assumes the select value is static during any given analysis — which is exactly the scenario STA can verify. The genuinely hard problem is what happens during the switch itself, while the system is running and needs to change clock source without stopping. An ordinary combinational MUX built from simple gates can produce a runt pulse on its output if the select signal changes while both input clocks happen to be at different phases — exactly the same class of glitch hazard discussed for clock gating in Lesson 4.6, but now with two live, independently-toggling clock sources instead of one clock and one static enable.

Because a live switch is inherently a dynamic, multi-clock-domain event, it cannot be verified by STA alone — STA only proves each static configuration is individually timing-clean. The switch transition itself requires a purpose-built glitch-free clock mux circuit, verified structurally (not purely by STA):

// Simplified glitch-free clock mux (Pausanias-style synchronizer mux) // Each clock path is independently gated OFF before the switch, // synchronized to its own domain, and only re-enabled after // confirming the other domain has also gone quiet. module glitch_free_clkmux ( input wire clk_a, clk_b, sel, rst_n, output wire clk_out ); wire en_a, en_b; // Each side has its own 2-flop sync chain sampling the // OPPOSITE side's "quiet" acknowledgment before enabling, // guaranteeing both gated clocks are LOW before the mux // output can switch which one is active. clk_switch_half u_half_a (.clk(clk_a), .sel(~sel), .other_ack(en_b), .en(en_a)); clk_switch_half u_half_b (.clk(clk_b), .sel( sel), .other_ack(en_a), .en(en_b)); assign clk_out = (clk_a & en_a) | (clk_b & en_b); endmodule

This structure guarantees the output only ever passes full, complete pulses from whichever clock is currently selected, and never overlaps or truncates an edge during the handoff — at the cost of a few cycles of latency during the actual switch, which the system must tolerate.

4. Timing the glitch-free mux itself

Even a correctly designed glitch-free mux still needs conventional STA on its internal synchronizer flops (2-flop CDC synchronizers, exactly as covered in the CDC course) and on the final AND-OR combining logic. The output net is then declared with the appropriate create_clock or create_generated_clock statement per scenario, exactly as in Section 2 — the glitch-free structure solves the dynamic switching hazard; SDC scenario setup still solves the static analysis problem for whichever source ends up selected.

5. Common mistake: forgetting to constrain the "off" input

Even with set_case_analysis correctly fixing the select pin, engineers sometimes forget that the unselected clock's source is often still physically toggling elsewhere in the design (feeding other domains). If that unselected clock isn't separately declared and time in its own right somewhere in the SDC, any logic it happens to feed outside the mux goes completely unanalyzed. A thorough SDC review always checks that every physical clock source in the design has a create_clock statement covering it in every scenario where it is physically active, not just the scenario where it happens to be the selected mux input.
