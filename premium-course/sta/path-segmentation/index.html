STA / Module 8: Timing Exceptions
Lesson 8.9

Path Segmentation

A raw report_timing dump can be hundreds of lines of cell and net delays. Path segmentation is the mental (and sometimes literal, tool-supported) framework for breaking that dump into three independently-understandable pieces — and it is the fastest diagnostic technique for figuring out whether a violation is a logic problem, a clock problem, or a constraint problem before you touch a single gate.

1. The three segments of every timing path
SegmentSpansWhat lives here
Launch clock segmentClock source → launch flop's CP (clock) pinClock tree buffers, clock gating cells, generated-clock dividers on the launch side
Data segmentLaunch flop's Q pin → capture flop's D pinOrdinary combinational logic: gates, muxes, adders — the "real" logic path most RTL engineers think of as "the timing path"
Capture clock segmentClock source → capture flop's CP pinClock tree buffers, gating, dividers on the capture side — structurally identical in kind to the launch clock segment, but a different physical branch of the tree

Every report_timing output is, underneath its line-by-line format, always exactly these three segments stacked together: the launch clock segment builds up to "data arrival time" (combined with the data segment), and the capture clock segment builds up to "data required time," with slack being the difference between the two totals.

2. Why segmentation is the fastest debug technique

When a path violates, the instinctive reaction is to look at the data segment and start upsizing gates or restructuring logic. This is often wrong, or at best inefficient, because a large fraction of real-world violations actually originate in one of the clock segments, not the data segment:

  • If the launch or capture clock segment has an unusually large delay compared to sibling paths on the same clock, the root cause may be a clock tree imbalance (Lesson 4.2) or an unbalanced CTS branch — no amount of data-path optimization fixes a clock tree problem, and engineers who don't segment the path first can burn significant effort resizing perfectly fine data logic.
  • If the data segment is short but slack is still deeply negative, check clock uncertainty and skew contributions first (Lessons 4.2 and 4.5) — sometimes the constraint itself (an overly conservative uncertainty value, or a missing generated-clock relationship) is manufacturing a violation that doesn't reflect any real physical problem.
  • If the data segment dominates and is genuinely long, that's the signal to actually pursue data-path fixes: pipelining, logic restructuring, upsizing (Lessons 12 and 13).
Rule of thumb: before touching any gate, compare the launch and capture clock segment delays for the violating path against the typical clock segment delay for other paths on the same clock (visible via report_clock_timing or by scanning several unrelated report_timing outputs on the same clock). If this path's clock segment is a noticeable outlier, you are very likely looking at a clock tree problem being misdiagnosed as a logic problem.
3. Segment-level reading of a full report
Startpoint: reg_A (rising edge-triggered flip-flop clocked by CLK) Endpoint: reg_B (rising edge-triggered flip-flop clocked by CLK) Path Group: CLK Path Type: max (Setup Check) Point Incr Path ----------------------------------------------------------- clock CLK (rise edge) 0.00 0.00 \ clock network delay (propagated) 0.85 0.85 > LAUNCH CLOCK SEGMENT (0.85ns) reg_A/CP 0.00 0.85 / ----------------------------------------------------------- reg_A/Q 0.12 0.97 \ U1/Y 0.31 1.28 | U2/Y 0.27 1.55 > DATA SEGMENT (0.70ns: 0.12+0.31+0.27) reg_B/D 0.00 1.55 / data arrival time 1.55 ----------------------------------------------------------- clock CLK (rise edge) 2.00 2.00 \ clock network delay (propagated) 0.22 2.22 > CAPTURE CLOCK SEGMENT (0.22ns) reg_B/CP 2.22 / clock uncertainty -0.08 2.14 library setup time -0.10 2.04 data required time 2.04 ----------------------------------------------------------- slack (MET) 0.49

Segmented this way, an obvious problem jumps out: the launch clock segment (0.85ns) is much larger than the capture clock segment (0.22ns) — a huge, negative-skew-producing imbalance on this specific register pair. If this path were failing, the very first thing to check is why reg_A's clock branch takes nearly 4x longer to reach it than reg_B's branch — almost certainly a CTS balancing issue, not a data logic issue, even though the data segment itself (0.70ns across two gates) looks unremarkable.

4. Segmentation and timing exceptions

Path segmentation also clarifies where timing exceptions apply. A set_false_path or set_multicycle_path declaration (Lessons 8.1-8.8) is always really a statement about the data segment's relationship to the clock segments — for example, a multicycle path says "the data segment is allowed to take N clock periods instead of 1, so extend the capture clock segment's effective required time by (N-1) periods." Thinking in segments makes it much easier to reason about whether a proposed exception is legitimate (reflecting a real architectural relationship) or is being used to paper over what is actually a genuine, unaddressed clock or data segment problem.

5. Segmentation in PrimeTime debug commands
# Isolate just the clock network delay component for a path's endpoint, # without wading through the full report_timing text output: get_attribute [get_pins reg_B/CP] clock_latency -min_max max # Compare launch vs capture clock latency directly across # a batch of endpoints to spot outlier clock segments fast: report_clock_timing -type latency -clock CLK
