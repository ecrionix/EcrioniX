Lesson 4.3

Clock Jitter (Deterministic vs. Random)

Jitter is the short-term, cycle-to-cycle variation of a clock edge's actual position relative to where it should ideally be. Unlike skew, which is a fixed spatial difference between two flops, jitter is a temporal uncertainty on a single clock edge itself — and because it can never be fully characterized or eliminated, STA handles it not by modeling it exactly, but by budgeting for its worst case as uncertainty.

1. What jitter actually is

An ideal clock has every rising edge separated from the next by exactly the same period, forever. Real clocks — especially those generated by an on-chip PLL — do not. The PLL's voltage-controlled oscillator (VCO), reference clock noise, and loop-filter dynamics all introduce small, cycle-to-cycle timing errors. The result is that edge N might arrive 8 picoseconds early, edge N+1 might arrive 3 picoseconds late, and so on, in a way that is not predictable cycle-by-cycle but is bounded statistically over a long observation window.

Jitter is normally specified as a peak-to-peak or RMS (root-mean-square) value in the PLL's datasheet, for example "12ps RMS period jitter" or "45ps peak-to-peak cycle-to-cycle jitter." STA does not simulate the PLL — it consumes this datasheet number and folds it into the timing margin at every flop the clock reaches.

2. Deterministic Jitter (DJ) — bounded and traceable

Deterministic jitter has an identifiable, repeatable cause and — critically — a bounded, finite peak-to-peak value. If you know the cause, you can (in principle) predict its magnitude. Common sources:

  • Power supply noise / simultaneous switching noise (SSN) — every time a large block of logic switches, it draws a current spike from the supply rail, causing a small transient voltage droop. Because gate delay (including the PLL's own internal delay stages) depends on supply voltage, this droop directly perturbs the clock edge timing. This is usually the single largest DJ contributor on a digital SoC.
  • Crosstalk-induced jitter — aggressor nets switching near the clock distribution network couple charge onto clock wires, shifting the effective threshold-crossing time of the clock edge (see Lesson 9 on crosstalk delay).
  • Duty cycle distortion (DCD) — asymmetric rise/fall characteristics in clock buffers cause the high and low phases of the clock to differ slightly from the ideal 50/50 split, which shows up as a periodic jitter component correlated with the clock pattern itself.
  • Inter-symbol interference (ISI) / data-dependent jitter — more relevant to high-speed serial I/O clocks than core clocks, but present in SerDes reference clock distribution.
Why DJ is "bounded": Because each DJ source has a physical maximum (maximum possible IR drop, maximum crosstalk coupling for a given aggressor swing), the sum of all DJ sources has a hard peak-to-peak ceiling. This matters enormously for signoff — a bounded quantity can be added directly (worst-case, deterministically) to the timing budget.
3. Random Jitter (RJ) — unbounded and statistical

Random jitter arises from fundamental physical noise processes that have no hard maximum: thermal noise in the PLL's VCO transistors, flicker (1/f) noise, and shot noise. RJ is typically modeled as a Gaussian-distributed random variable, characterized by its standard deviation (σ, "sigma"), not a peak-to-peak bound.

The core problem with RJ: a true Gaussian distribution has non-zero probability density stretching to infinity in both directions. There is, strictly speaking, no finite peak-to-peak value for random jitter — a sufficiently rare (but non-zero-probability) event could in principle produce an arbitrarily large jitter excursion. STA needs a single worst-case number to add to the timing budget, so the industry converts RJ into an effective peak-to-peak value using a chosen confidence level, almost always expressed as a multiple of sigma.
Confidence multiplierProbability of exceeding boundTypical use
±3σ~2.7 × 10⁻³Loose consumer-grade margin — rarely used for sign-off alone
±7σ~2.6 × 10⁻¹²Common minimum for enterprise/networking ASIC signoff
±14σ~1.6 × 10⁻⁴⁴Very common convention in modern PLL datasheets and high-reliability signoff

The RJ peak-to-peak value used in timing budgets is therefore: RJ_pp = N × σ for whatever N-sigma confidence the project's signoff methodology requires. This N-sigma number is then combined with DJ (usually by direct addition, sometimes root-sum-square depending on methodology conservatism) to arrive at a single total peak-to-peak jitter figure, Total Jitter (TJ).

4. How STA actually consumes jitter: set_clock_uncertainty

STA does not model jitter as a probability distribution during path tracing — that would make the analysis non-deterministic, defeating the entire point of static timing analysis. Instead, the total jitter number (TJ, derived above) is folded into a single fixed derating value applied uniformly to every path launched or captured by that clock, using the set_clock_uncertainty SDC command:

# TJ = DJ + N*sigma(RJ), e.g. 45ps DJ + 14*3ps RJ = 45 + 42 = 87ps total jitter # Clock period = 1000ps (1GHz) set_clock_uncertainty -setup 0.087 [get_clocks CLK] set_clock_uncertainty -hold 0.020 [get_clocks CLK]

Notice the setup and hold uncertainty values are usually different. Setup uncertainty typically includes the full jitter budget plus margin for OCV/skew pessimism, because setup checks against a full clock period and jitter directly eats into that period. Hold uncertainty is often a smaller, separately-derived number because hold checks operate within a single edge and different components of jitter (particularly period jitter vs. cycle-to-cycle jitter) apply differently to same-edge vs. next-edge relationships.

Cycle-to-cycle jitter vs. period jitter: These are not the same number and using the wrong one is a classic sign-off mistake. Period jitter measures deviation of a single period from the ideal — relevant to setup, which spans one full period. Cycle-to-cycle jitter measures the difference between two consecutive periods — this is the number that matters for back-to-back edge relationships and is usually the correct one to apply for hold-adjacent uncertainty terms. PLL datasheets report both; picking the wrong column is a real, recurring error in early-career STA work.
5. Why jitter erodes both setup and hold slack — never helps

Unlike skew (which trades setup margin for hold margin depending on sign), clock uncertainty from jitter is applied as a pure subtraction on both checks:

Setup Slack = (T_clk - Uncertainty_setup - T_setup) - T_data_path Hold Slack = T_data_path - (T_hold + Uncertainty_hold)

This is because jitter represents genuine unpredictability in edge position — it can move the capture edge earlier (hurting setup, since less time is available) or later (hurting hold, since the data-invalid window after the launch edge grows) on any given real cycle, and STA must guard against the worst case in both directions simultaneously. This is exactly why jitter is treated so differently from skew in the margin equations: skew has a known sign per path; jitter's sign is unknown and must be assumed adversarial on every check.

6. Where jitter budget comes from in a real SoC
  1. PLL datasheet supplies raw period jitter and cycle-to-cycle jitter numbers (RMS and/or peak-to-peak) at a given reference frequency and loop bandwidth setting.
  2. Clock distribution network adds its own jitter contribution as the clock propagates through buffers — each buffer stage adds a small amount of additive jitter from its own supply noise sensitivity, which accumulates (root-sum-square, generally) with distance from the PLL.
  3. Signal integrity / crosstalk analysis contributes the deterministic jitter component from coupling onto clock nets, computed separately (Lesson 9) and folded into the DJ budget.
  4. The final combined number is handed to the STA team, who apply it via set_clock_uncertainty — closing the loop from silicon-level PLL characterization all the way to a single SDC constraint.
