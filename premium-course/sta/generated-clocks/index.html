STA / Module 4: Advanced Clocking
Lesson 4.7

Generated Clocks (Dividers)

Not every clock in a design comes straight from a PLL pin. Divide-by-N counters, clock-gating cells, and clock muxes all produce new clock waveforms derived from an existing clock — and STA cannot correctly time any of them unless you explicitly tell it how the derived clock relates to its source using create_generated_clock.

1. Why STA can't infer a generated clock on its own

STA treats any pin declared with create_clock as a clock source and propagates it through the design. But a divide-by-2 counter's output is just ordinary combinational/sequential logic to the tool — the same kind of signal as any data pin — unless you explicitly declare it as a clock. If you don't, two things go wrong simultaneously: (1) the divided signal is treated as ordinary data and checked for setup/hold against the undivided clock, which is nonsensical, and (2) anything downstream that the divided signal actually clocks receives no clock propagation at all, so PrimeTime reports it as unclocked and skips timing it entirely — a silently unchecked region of the design.

2. The command: create_generated_clock
# Master clock: 1GHz at the PLL output pin create_clock -name CLK_PLL -period 1.0 [get_pins u_pll/CLK_OUT] # Divide-by-2 clock generated by a toggle flop off CLK_PLL create_generated_clock -name CLK_DIV2 \ -source [get_pins u_pll/CLK_OUT] \ -divide_by 2 \ [get_pins u_div_ff/Q] # Divide-by-3 (non-integer duty cycle) needs an explicit edge list instead create_generated_clock -name CLK_DIV3 \ -source [get_pins u_pll/CLK_OUT] \ -edges {1 4 7} \ [get_pins u_div3_ff/Q]

Every generated clock declaration needs two pieces of information: -source, the master clock pin this new clock is derived from (STA uses this to know how the master's jitter, latency, and uncertainty propagate into the generated clock), and either -divide_by / -multiply_by for simple integer ratios, or an explicit -edges list for anything asymmetric or non-integer.

3. Understanding -edges for non-50% duty cycle dividers

The -edges list specifies which edges of the master clock correspond to which edges of the generated clock, counted in master-clock half-periods starting from edge 1. For a divide-by-3 clock (period = 3 × master period) with a 33% duty cycle (high for 1 master period, low for 2), the generated clock has a rising edge at master edge 1, a falling edge at master edge 4, and its next rising edge at master edge 7:

Generated clock (DIV3)rise——fall——rise (next period)

Getting this edge list wrong is a very easy, very common mistake — an off-by-one in the edge list produces a generated clock with the wrong period or duty cycle in the STA model, even though the RTL logic itself is completely correct. STA is only as accurate as the SDC that describes it; a wrong -edges list makes a functionally correct divider look broken (or worse, look correct when it isn't).

4. Generated clocks and clock uncertainty inheritance

A generated clock's own set_clock_uncertainty is usually specified independently, but conceptually its jitter is inherited (and often amplified) from the master clock plus whatever additional jitter the divider logic itself contributes. If the master clock has 40ps of jitter, a divide-by-2 clock does not automatically have 20ps — the divider is a synchronous digital circuit, and its output edge timing error is generally comparable to or slightly larger than the master's, because the divider's own flop adds its own clock-to-Q variation on top. This is a frequent source of confusion: engineers sometimes assume dividing a clock "divides" its jitter proportionally, which is not how digital dividers work.

5. Path checks across a generated-to-master clock boundary

When a timing path launches from a flop on the generated clock and captures on a flop on the master clock (or vice versa), STA must determine the correct clock relationship between the two — which edges of each clock can legally align. Because a generated clock is derived from the master using a well-defined mathematical relationship (divide ratio + edge list), PrimeTime can compute this relationship automatically and finds the correct, tightest legal timing check without the engineer needing to declare a separate multicycle path — as long as the generated clock was declared correctly in the first place. This automatic relationship is one of the strongest reasons to always use create_generated_clock for divided/gated clocks rather than trying to model them as independent, unrelated clocks with create_clock.

Anti-pattern to avoid: declaring a divided clock as a brand-new, independent create_clock instead of a proper create_generated_clock. This breaks the mathematical relationship between the two clocks, forcing STA to treat every crossing between them as an asynchronous, unrelated-clock path — which typically requires manual false-path or multicycle-path exceptions to avoid a flood of meaningless, unachievable timing violations. It also silently hides real timing risk if the false-path exception is applied too broadly.
6. Verifying the generated clock is correct
report_clocks -attribute # Confirms period, waveform, source, and master/generated relationship # for every declared clock in the design — the first sanity check # any STA engineer should run after writing new clock SDC.
