RTL Design — where you will live in this course

RTL design is the craft of describing digital hardware in a hardware description language so tools can simulate it and later implement it. This is your home base for the rest of the course.

RTL means

Register-Transfer Level — you describe how data moves between registers each clock, and what combo logic sits between them.

Register-Transfer Level = describe how data moves between flops each cycle.

1

A day in the life (realistic)

  1. Read a micro-spec / ticket for a block.
  2. Sketch FSM or datapath on paper.
  3. Code Verilog; keep synthesizable style.
  4. Write or extend a testbench; run waves.
  5. Run lint; fix latch / width / clock issues.
  6. Send for peer review; address comments.
  7. Hand to verification / synthesis with known open issues listed.
💡 Craft analogy

You are both author and first QA. Shipping untested RTL is like publishing a book without spellcheck.

Collaboration map

  • DV: You provide RTL + micro-arch doc; they scale tests. Agree on CSR golden model early.
  • PD: You register outputs and document clocks; they ask for pipeline stages on long paths.
  • DFT: You avoid latches and document async resets; they insert scan and ask for test mode muxes.
  • Software: Register map is ABI — changing bit positions without notice breaks firmware.
🎤 Meeting angle

End standups with “open issues” — not just “still coding.” List: lint waivers pending, CDC review needed, TB not updated for M4.

Example of clean, synthesizable style you will practice — a loadable counter:

load_counter.v
module load_counter #(
  parameter WIDTH = 8
)(
  input  wire             clk,
  input  wire             rst_n,
  input  wire             load,
  input  wire             en,
  input  wire [WIDTH-1:0] din,
  output reg  [WIDTH-1:0] count
);
  always @(posedge clk or negedge rst_n) begin
    if (!rst_n)
      count <= {WIDTH{1'b0}};
    else if (load)
      count <= din;
    else if (en)
      count <= count + 1'b1;
  end
endmodule

Combo vs sequential — two coding styles

combo_vs_seq.v
// COMBO: always @(*) or assign — no clock, updates when inputs change
assign sum = a + b;

// SEQ: always @(posedge clk) — state updates only on clock edge
always @(posedge clk or negedge rst_n)
  if (!rst_n) q <= 1'b0;
  else        q <= d;

FSM snippet (synthesizable two-process style)

fsm_two_process.v
module fsm_two_process (
  input  wire clk, rst_n, go,
  output reg  busy
);
  localparam IDLE = 1'b0, RUN = 1'b1;
  reg state, next;

  always @(posedge clk or negedge rst_n)
    if (!rst_n) state <= IDLE;
    else        state <= next;

  always @(*) begin
    next = state;
    busy = 1'b0;
    case (state)
      IDLE: if (go) next = RUN;
      RUN:  begin busy = 1'b1; next = IDLE; end
      default: next = IDLE;
    endcase
  end
endmodule

What “good RTL” optimizes for

📖

Clarity

Teammates understand intent without archaeology.

⚙️

Synthesizability

Maps cleanly to flops and gates.

⏱️

Timing friendliness

Avoids accidental mega-combo clouds.

🧪

Verifiability

Observable, reset-clean, asserts possible.

Coding standards highlights

  • One module per file; module name = file name
  • Non-blocking <= in sequential blocks; blocking = in combo
  • Full case / default in FSMs — no inferred latches
  • Explicit widths on literals (8'd0 not bare 0)
  • Reset strategy documented (sync vs async, active level)
  • No delays (#10) in synthesizable RTL

Review-ready checklist

  • Spec MUST lines traced in header comment
  • Unit TB passes; waves captured for main scenario
  • Lint clean or waivers justified
  • No TODO on critical paths without ticket number
  • Register map matches architecture doc
💼 Interview angle

“What makes RTL reviewable?” — Mention separation of combo/seq, FSM structure, reset, and tests included in the PR.

What RTL is NOT

  • Not a software program that “runs line by line” on a CPU (simulation looks sequential; hardware is parallel).
  • Not the final gates — synthesis decides many library cells.
  • Not complete without verification evidence.

Mindset shift: you describe hardware structure and timed behavior, not algorithms in the software sense alone.
