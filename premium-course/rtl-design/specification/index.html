Lesson 1.2

Specification — writing requirements design can implement

Bad specs create endless RTL thrash. A good spec is not a novel — it is a contract: what the design must do, how fast, on which pins, and how you will know it is done.

1

What belongs in a useful spec

Spec quality = how clearly you can turn MUST lines into tests.

  • Purpose — one paragraph: who uses this IP and why.
  • Features — numbered list of behaviors (must / should / nice-to-have).
  • Interfaces — clocks, resets, buses, protocols (e.g. I2C pins, IRQ).
  • Performance — throughput, latency, max clock, timing modes.
  • Power / modes — sleep, clock gating expectations (even if light).
  • Error / corner cases — NACK, clock stretch, illegal commands.
  • Acceptance tests — how verification will prove success.

Trap: “Make it work like the competitor chip” with zero numbers. That is not a spec — it is a wish.

2

Requirements language that prevents fights

✅

MUST

Non-negotiable. Missing it is a bug.

🟡

SHOULD

Strong preference; skip only with written reason.

💡

MAY

Optional. Nice for v2.

Example: “The I2C master MUST generate START/STOP per Spec Rev 1. The UI MAY expose a debug counter.”

3

Spec → RTL: the handoff question

Before coding, a designer should answer:

  1. What are the inputs/outputs and their reset values?
  2. What clocks/domains exist?
  3. What sequences are legal vs illegal?
  4. What does “pass” look like in simulation?
💡 Restaurant menu analogy

A menu that says “tasty food” cannot be cooked consistently. A menu that lists ingredients, sizes, and allergens can. Specs are menus for silicon.

4

Mini exercise (I2C foreshadow)

Write 5 MUST lines for an I2C master (even if rough). Example starter:

  • MUST support 7-bit addressing
  • MUST detect ACK/NACK after each byte
  • MUST allow software to abort a hung transfer

Keep this list — Module 11 will turn it into a real one-page spec.

Here is how a real (tiny) I2C master micro-spec might start — copy this style into your notes:

i2c_master_spec.txt
IP: i2c_master_v1
PURPOSE: Let software read/write I2C sensors on the board.

MUST:
  M1. Support 7-bit addressing, standard-mode (100 kHz target)
  M2. Generate START, STOP, repeated-START per I2C timing rules
  M3. Detect ACK/NACK after every address and data byte
  M4. Expose BUSY and NACK sticky status bits in CSR
  M5. Allow software abort of a hung transfer (ABORT bit)

SHOULD:
  S1. Support clock stretching from slave
  S2. Interrupt on DONE / NACK

MAY:
  X1. Debug byte counter (v2)

ACCEPTANCE:
  A1. Directed TB: START -> addr+W -> data -> STOP, ACK path PASS
  A2. Directed TB: slave NACK sets sticky NACK, clears BUSY
  A3. Abort during BUSY returns FSM to IDLE within 1 byte time

🎯 What to remember

  • A spec is a contract: features, interfaces, performance, corners, acceptance.
  • Use MUST/SHOULD/MAY to avoid ambiguous fights.
  • If you cannot test it, you cannot claim it.
  • Next: architecture — blocks, interfaces, clocks, power domains.
