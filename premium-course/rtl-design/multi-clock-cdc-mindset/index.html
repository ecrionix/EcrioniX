Lesson 9.5

Why multi-clock chips exist (CDC mindset for designers)

No real SoC runs on one clock. CPUs, DRAM, PCIe, and sensor blocks each need their own frequency — and every boundary between them is a CDC problem you must design, not hope DV finds.

Clock-domain crossing (CDC)

A signal generated in clock domain A sampled by logic in clock domain B without a guaranteed phase relationship. Without proper synchronizers, metastability can corrupt data.

1

Why SoCs are multi-clock

A single global clock at max frequency would burn power and fail timing on slow peripherals. Engineers partition by function and pick the slowest clock that meets each block's throughput target.

Power, timing, and protocol requirements force multiple clocks. Integration creates dozens of CDC interfaces.

⚡

Power

Slower clocks = lower dynamic power. Gate domains independently.

📡

Protocol

PCIe, DDR, UART each mandate specific frequencies.

⏱️

Timing

Not every path needs 2 GHz. Partition by criticality.

BlockTypical clockWhy separate
CPU coreHigh (GHz)Performance-critical compute
Peripheral busMedium (100s MHz)GPIO, SPI, I2C don't need GHz
Always-onLow (kHz)Wake logic runs while main core sleeps
PHY interfacesProtocol-definedCannot be arbitrarily changed
2

Metastability — the physical problem

When a signal changes near the receiving clock edge, the capturing flop may enter a metastable state — output neither solid 0 nor 1 for an unbounded (but exponentially unlikely) time. One bad sample can corrupt a state machine or counter.

Trap

Simulation models metastability as zero-delay or X-prop — neither matches silicon. A CDC bug can pass 100% sim coverage and still fail in the field.

CDC is a design concern — not only DV

Verification can inject random metastability and run formal CDC tools — but someone must write the synchronizer RTL first. That someone is the designer at the domain boundary.

RoleCDC responsibility
RTL designerChoose sync structure (2FF, pulse, handshake, FIFO)
Integration leadMap all crossings; ensure SDC clock groups match
DV engineerCDC-focused sim, protocol checkers, coverage of crossings
SignoffSpyGlass CDC / Jasper formal CDC — lint + structural proof
cdc_bad_designer.v
// BAD — designer throws signal across domains, hopes DV catches it
// In clk_cpu domain:
reg irq_cpu;
always @(posedge clk_cpu) irq_cpu <= peripheral_irq;  // async!

// BAD — multi-bit bus without gray/FIFO
always @(posedge clk_sys)
  status_vec <= counter_from_slow_clk;  // bits arrive at different times
cdc_good_designer.v
// GOOD — designer owns the crossing
// 1-bit level: 2-flop sync (lesson 9.6)
reg irq_meta, irq_sync;
always @(posedge clk_cpu or negedge rst_n) begin
  if (!rst_n) {irq_meta, irq_sync} <= 2'b00;
  else        {irq_meta, irq_sync} <= {peripheral_irq, irq_meta};
end

4

Designer CDC checklist at block boundaries

  • Document every output that leaves your clock domain
  • 1-bit levels → 2-flop synchronizer in receiving domain
  • Pulses → pulse synchronizer (not raw 2FF on a 1-cycle pulse)
  • Multi-bit data → handshake, gray counter, or async FIFO
  • Never synchronize a bus bit-by-bit with separate 2FF chains
  • Add CDC_SYNC comments lint tools can match
  • Run CDC lint before handing block to integration
▶ Prototype synchronizers in simulator
5

Frequency ratios and clock relationships

Not all multi-clock systems are fully asynchronous. Understanding the relationship between domains helps pick synchronizers and set constraints.

RelationshipExampleDesign note
Synchronousclk and clk/2 from same PLLSTA handles; still document phase
Rational100 MHz and 25 MHz (÷4)May use simpler sync; verify with STA
AsynchronousCPU clk + crystal UARTFull 2FF / handshake / FIFO required
Gated / dynamicPower-gated domainIsolation + retention; RDC lint
Trap

Assuming two clocks are "close enough" because they're both on the chip. If they come from different oscillators or PLL outputs with no phase lock, treat them as asynchronous.

Reset-domain crossing (RDC): Async reset deassert without synchronizer is a cousin of CDC. Lint tools (Questa RDC, SpyGlass) flag reset paths that cross domains unsynchronized — same designer-owned mindset applies.

block_boundary_inst.v
// Integration view — designer owns synchronizer inside boundary
module uart_top (
  input  wire       clk_cpu,
  input  wire       clk_uart,   // async to cpu
  input  wire       rst_n,
  input  wire       tx_valid_cpu,
  input  wire [7:0] tx_data_cpu,
  output wire       tx_busy_cpu
);
  // All clk_uart ↔ clk_cpu crossings use named sync modules
  sync_2ff      u_busy_sync  (.clk_dst(clk_cpu), ...);
  pulse_sync    u_tx_pulse   (.clk_src(clk_cpu), .clk_dst(clk_uart), ...);
  // Never: assign tx_data_uart = tx_data_cpu;  // raw bus — lint ERROR
endmodule

These five checkboxes are what integration leads verify when your block connects to the SoC. Fill them in proactively — don't wait for CDC lint to find gaps.

🎯 What to remember

  • Multi-clock SoCs are mandatory — power, protocol, and timing demand it.
  • Metastability is real; sim hides it. Design synchronizers, don't rely on luck.
  • CDC is designer-owned at the boundary; DV and signoff verify your choices.
  • 1-bit ≠ multi-bit — different sync structures for each.
