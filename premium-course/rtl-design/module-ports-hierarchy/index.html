RTL Design / Module 3: Verilog from Scratch
Lesson 3.1

Module, ports & hierarchy — your first file

Every Verilog design is a tree of modules. A module is a reusable block with a port list (the boundary pins) and an internal body. Today you write your first complete DUT + testbench and learn how parent modules wire children together.

Definition

A module is the fundamental building block of RTL — like a function with hardware pins. module ... endmodule wraps everything.

1

The module skeleton

Every synthesizable file starts with a module declaration. The name becomes the cell type in the netlist. Ports are the only signals that cross the boundary.

module_skeleton.v
module my_block (
  input  wire       clk,
  input  wire       rst_n,
  input  wire [7:0] data_in,
  output wire [7:0] data_out
);
  // internal logic lives here
endmodule
KeywordRoleNotes
moduleOpens a design unitName must be unique in the project (usually)
endmoduleCloses the unitRequired — missing it is a syntax error
inputSignal driven from outsideCannot be assigned inside the module
outputSignal driven from insideNeeds a driver: assign or always
inoutBidirectional pinTristate buses — advanced; avoid early
Analogy

Think of a module as a chip package: the ports are the pins on the package, and the body is the silicon inside. Parent modules solder wires between child packages.

2

Port directions — who drives what

Direction tells the compiler who is allowed to assign each net. Violating this causes elaboration errors or simulation X-propagation.

Input = driven from outside. Output = driven from inside. Inout = shared bus with tristate control.

DirectionDriverTypical useBeginner?
inputParent / TBClocks, data, control✓ daily
outputThis moduleResults, status flags✓ daily
inoutEither side (tristate)I²C, shared memory busLater
Trap

Assigning to an input port inside the module is illegal. If you need to modify an input, copy it to an internal wire first.

3

ANSI vs non-ANSI port style

Verilog-2001 introduced ANSI ports — direction and type in the port list. Older style declares ports first, then types separately. Both work; ANSI is standard in modern code.

ansi_vs_nonansi.v
// --- ANSI style (preferred) ---
module adder_ansi (
  input  wire [3:0] a,
  input  wire [3:0] b,
  output wire [4:0] sum
);
  assign sum = a + b;
endmodule

// --- Non-ANSI style (legacy) ---
module adder_legacy (a, b, sum);
  input  [3:0] a, b;
  output [4:0] sum;
  wire [4:0] sum;  // output must be wire or reg
  assign sum = a + b;
endmodule
StylePort listBody declaresWhen to use
ANSIinput wire [7:0] dataNothing extra for portsAll new code
Non-ANSI(clk, rst, q) names onlyinput clk; output q;Legacy IP, auto-translated netlists

Tip: Parameters go before the port list: module foo #(parameter W=8) (...). We'll use this pattern throughout the course.

4

Hierarchy — instantiating children

A top-level module instantiates child modules by name. Each instance is a separate copy of the hardware — like stamping the same chip multiple times on a board.

Parent declares wires; children connect via named port maps (.port(signal)).

hierarchy_example.v
module half_adder (
  input  wire a, b,
  output wire sum, cout
);
  assign sum  = a ^ b;
  assign cout = a & b;
endmodule

module full_adder (
  input  wire a, b, cin,
  output wire sum, cout
);
  wire s1, c1, c2;

  half_adder u_ha (.a(a),  .b(b),   .sum(s1),  .cout(c1));
  half_adder u_hb (.a(s1), .b(cin), .sum(sum), .cout(c2));
  assign cout = c1 | c2;
endmodule

Two connection styles exist:

  • Named port map (preferred): .port_name(wire_name) — order-independent, self-documenting.
  • Positional: half_adder u_ha (a, b, s1, c1); — fragile if port order changes.

Instance names (u_ha) are required for simulation waveforms and synthesis reports. Always name your instances.

5

Hierarchical names — dot notation

In simulation and debug, you reference signals inside instances with hierarchical paths: top.child.grandchild.signal.

hier_paths_tb.v
// In a testbench or $display / waveform viewer:
//   dut.u_core.u_alu.result
//   dut.u_core.clk
//
// SystemVerilog assertion example:
// assert property (@(posedge clk) dut.u_fifo.empty == 0);

module tb;
  reg  a, b, cin;
  wire sum, cout;

  full_adder dut (.a(a), .b(b), .cin(cin), .sum(sum), .cout(cout));

  initial begin
    a = 0; b = 0; cin = 0; #10;
    a = 1; b = 1; cin = 0; #10;
    // Waveform: expand dut → u_ha → internal wires
    $display("sum=%b cout=%b", sum, cout);
    $finish;
  end
endmodule
Path segmentMeaningExample
Module instanceA child blockdut.u_alu
Generate blockArray of instancesgenblk[3].u_cell
SignalWire or reg insidedut.u_fifo.count
Debug tip

In GTKWave or your simulator GUI, the hierarchy tree mirrors the source structure. If you can't find a signal, check whether it's declared inside the right instance scope.

6

Your first complete DUT + testbench

A Device Under Test (DUT) is the design you're verifying. The testbench (TB) is a separate module that instantiates the DUT, drives inputs, and checks outputs. TB is not synthesized — it can use delays (#), $display, and $finish.

and_gate_dut.v
// --- DUT: synthesizable ---
module and_gate (
  input  wire a, b,
  output wire y
);
  assign y = a & b;
endmodule
and_gate_tb.v
// --- TB: simulation only ---
module and_gate_tb;
  reg  a, b;
  wire y;

  and_gate dut (.a(a), .b(b), .y(y));

  initial begin
    $dumpfile("and_gate.vcd");
    $dumpvars(0, and_gate_tb);
  end

  initial begin
    a = 0; b = 0; #10;
    if (y !== 0) $error("FAIL: 0&0");
    a = 1; b = 0; #10;
    if (y !== 0) $error("FAIL: 1&0");
    a = 1; b = 1; #10;
    if (y !== 1) $error("FAIL: 1&1");
    $display("All tests passed");
    $finish;
  end
endmodule
▶ Run in Verilog Simulator
DUT module→ TB instantiates DUT→ Simulator runs TB→ Waveforms + checks
  • DUT has only input/output ports — no TB constructs
  • TB drives inputs with reg (or logic in SV)
  • TB connects to DUT outputs with wire
  • Use #delay only in TB, never in synthesizable RTL
7

Parameters and generate preview

Modules can be parameterized — one RTL description, many sizes. You'll use this heavily for buses and counters.

param_mux.v
module mux2 #(
  parameter WIDTH = 8
)(
  input  wire [WIDTH-1:0] a, b,
  input  wire             sel,
  output wire [WIDTH-1:0] y
);
  assign y = sel ? b : a;
endmodule

// Instantiate with override:
// mux2 #(.WIDTH(16)) u_mux (...);
Trap

Forgetting the #() when overriding parameters: mux2 #(.WIDTH(32)) u (...) not mux2(.WIDTH(32)).

8

File organization habits

Small designs: one file per module. Larger designs: group related modules, one module per file named after the module.

FileContainsSynthesized?
and_gate.vDUT onlyYes
and_gate_tb.vTB onlyNo
top.vTop + child instancesYes
defines.vh`define macrosPreprocessed
Industry habit

RTL engineers keep TB out of synthesis file lists. Your Makefile or tool script compiles DUT files for synth and adds TB only for sim.

🎯 What to remember

  • module/endmodule wraps every design unit; ports define the boundary.
  • input = driven from outside; output = driven from inside.
  • Instantiate children with named port maps; use hierarchical paths for debug.
  • DUT is synthesizable; TB is simulation-only with delays and checks.
  • ANSI port style is the modern default — direction in the port list.
