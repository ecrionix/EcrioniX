Tips & Tricks for Verilog Coding Challenges

Match the port list exactly

Auto-grading connects your module to a hidden testbench by name and width. If the spec says output reg [3:0] out, don't change the width or direction — a mismatched port list fails instantiation before your logic is even simulated.

Blocking vs non-blocking is the #1 silent failure

Use <= in clocked always @(posedge clk) blocks and = in combinational always @(*) blocks. Mixing them can simulate "correctly" in simple tests and still fail on race-condition-sensitive hidden tests.

Always give combinational blocks a default assignment

Start every always @(*) block by assigning default values to all outputs, then override in specific branches. This avoids accidental latch inference when a case/if doesn't cover every condition.

Watch out for unintended latches

An incomplete if without an else, or a case without a default, inside a combinational block infers a latch — not a bug the simulator always flags loudly, but one that will fail timing-sensitive hidden tests.

Size your buses deliberately

An 8-bit sum from two 8-bit inputs needs 9 bits to hold carry-out. Read the spec's port widths carefully — truncation bugs are one of the most common ways a nearly-correct solution fails a hidden testbench.

Reset behavior matters, not just steady state

Hidden testbenches often check the very first few cycles after reset. Make sure every register has a defined, spec-correct value immediately after reset — don't rely on simulation's default initial value.

Use the online simulator to self-check first

Before submitting, paste your module into the online Verilog simulator with your own quick testbench. Catching a silly syntax or width bug yourself is faster than waiting on the grader.

FSMs: don't forget the "illegal state" path

If your state register can technically reach an unused encoding (common with non-one-hot encoding), hidden tests may deliberately force it there. Always define a default case that recovers back to a known-safe state.

Implementation Plan

  • Reuse the /run Icarus Verilog backend (already live on the simulator) — submit the student's module alongside a hidden testbench, parse a pass/fail marker from the output.
  • Each problem: a short spec, a starter module stub, and a hidden testbench the student never sees.
  • Start small — the CDC-tied module (category 6) ships first since those testbenches already exist from the CDC course.
  • Watch backend load: the simulator's HF Space sleeps on inactivity and has wake-up retry logic already; more frequent grading submissions here may need a queue or cooldown.
  • Track per-problem pass/fail in Firestore under completedChallenges, mirroring the completedLessons.cdc pattern already used for course progress.
  • This feature will eventually be free for everyone, not gated like CDC/RTL — the goal is open practice, not paid access.
  • Add a public leaderboard ranking users by challenges solved, to drive engagement and friendly competition.
